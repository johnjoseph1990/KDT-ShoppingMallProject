## 0. 이 문서를 쓰게 된 이유

과제 원문을 다시 읽어보면, **내가 실제로 만든 것과 문장이 안 맞는 지점이 여러 곳** 있다.
그런데 안 맞는 이유가 전부 같지는 않았다. 확인해보니 **성격이 다른 두 종류**가 섞여 있었다.

| 구분 | 성격 | 필요한 조치 | 건수 |
|---|---|---|---|
| **A. 과제 요구 ↔ 실제 구현** | 과제가 A라고 했는데 나는 **B를 선택**함 | **사유를 밝히고 동등성 논증** | 5건 |
| **B. 내 문서 주장 ↔ 실제 코드** | 내가 쓴 문서가 **코드보다 부풀려져 있음** | **사실대로 수정** (변명 아님) | 2건 |

**이 둘을 한 절에 섞어 쓰면 읽는 사람이 구분을 못 한다.**
"의도적으로 다르게 갔다"와 "내 문서가 틀렸다"는 심사자 입장에서 완전히 다른 신호이기 때문에,
아래에서 §1(A)과 §2(B)로 나눠 서술한다.

## 1. [A] 과제 요구 ↔ 실제 구현 — 다르게 간 5가지와 그 근거

각 항목을 **"과제 문장 → 내가 실제로 한 것 → 왜 → 학습 목표는 달성되는가"** 순으로 정리한다.
마지막 질문이 핵심이다. 과제의 문장을 안 지킨 게 아니라, **문장이 노리는 학습 목표를 다른 경로로 달성**했다는 걸 보여야 한다.

### A-1. 배포처 — "AWS" → **Azure** ⭐ 가장 눈에 띄는 차이

| | 내용 |
|---|---|
| **과제 문장** | Step 7-3: "애플리케이션을 **AWS**에 배포하고" |
| **실제** | **Microsoft Azure** — Container Apps + PostgreSQL Flexible Server + Blob Storage + DNS |
| **왜** | 수강 중인 KDT 과정의 **인프라 강의가 Azure 기준**이었다. 강의에서 배운 것을 그대로 적용·검증할 수 있는 환경이 Azure였고, 배운 걸 안 쓰고 처음 보는 AWS 콘솔을 더듬는 건 학습 효율이 나쁘다고 판단했다. |
| **학습 목표 달성 여부** | ✅ 달성. 클라우드 배포에서 배워야 할 것 — **컨테이너 이미지 빌드 → 레지스트리 푸시 → 관리형 DB 연결 → 환경변수 주입 → HTTPS 커스텀 도메인 연결** — 은 두 클라우드에서 동일한 개념이다. |

**서비스 1:1 대응** (이 표가 있으면 "AWS를 몰라서 피한 것"이 아님이 드러난다)

| AWS (과제 원문) | Azure (실제 사용) | 역할 |
|---|---|---|
| ECS / App Runner | **Azure Container Apps** | 컨테이너 실행 |
| ECR | **Azure Container Registry** | 이미지 저장소 |
| RDS for PostgreSQL | **PostgreSQL Flexible Server** | 관리형 DB |
| S3 | **Blob Storage** | 상품 이미지 |
| Route 53 + ACM | **Azure DNS + 관리형 인증서** | 도메인 + HTTPS |

**추가 근거:** 인프라를 포털 클릭이 아니라 **`azure/setup.sh` 스크립트 한 파일**로 남겼다.
→ "클라우드를 눌러봤다"가 아니라 "**같은 인프라를 코드로 재생성할 수 있다**"는 게 증명된다. 이게 원래 목표였다.

**결과:** https://www.minsdev.works — 상시 운영 중 (HTTPS 적용)

### A-2. UI 가이드 — "Vapor 학습·적용" → **학습 후 관리자 화면에만 부분 적용**

| | 내용 |
|---|---|
| **과제 문장** | Step 1-1: "Vapor(Goorm Design System)의 컴포넌트와 스타일 가이드를 **학습합니다**" |
| **실제** | 학습 후 설치까지 했으나, **적용은 관리자 화면(`AdminPage.jsx`)에 한정**. 사용자 화면 전체는 자체 CSS. |
| **왜** | 프로젝트 디자인 방향을 **Aesop 벤치마킹 · 미니멀 세리프 톤**으로 잡았고(`design/README.md`), 이 톤은 Vapor 기본 컴포넌트의 시각 언어와 결이 달랐다. 억지로 덮어쓰면 두 스타일이 충돌한다. 대신 **일관된 표·폼·버튼의 값어치가 가장 큰 관리자 CRUD 화면**에 Vapor를 썼다. |
| **학습 목표 달성 여부** | ✅ 달성. **과제 문장은 "학습합니다"이지 "전면 적용합니다"가 아니다.** 디자인 시스템을 "어디에 쓰면 이득이고 어디는 아닌지" 판단한 것 자체가 학습 결과다. |

**실측 근거** (문서에 쓰기 전에 확인한 수치)

```
@vapor-ui import 하는 파일 : 2개 / 전체 jsx 28개
  ├─ frontend/src/main.jsx        → '@vapor-ui/core/styles.css' (전역 스타일)
  └─ frontend/src/pages/AdminPage.jsx → Badge · Button · Tabs · Table · Textarea · TextInput

자체 스타일 : frontend/src/index.css · App.css
디자인 시안 : design/MINS Farmers Market.dc.html (인터랙티브 프로토타입, Aesop 톤)
```

> ⚠️ **이 항목은 §2의 B-1과 짝이다.** 판단 자체는 문제가 없는데, 기존 문서가 이걸
> "프론트 **전반**에 적용"이라고 써 놨던 게 문제였다. (수정 완료 — §2 참조)

### A-3. 결제 — "주문 완료 이후 결제 흐름 연결" → **실제 PG(토스페이먼츠) 연동**

| | 내용 |
|---|---|
| **과제 문장** | Step 4-3: "주문 완료 이후 **결제 및 처리 결과 흐름을 연결**합니다" |
| **내 초기 계획** | 기능 명세서에는 **모의 결제(P1)** 로 잡았다 (`FUNCTIONAL_SPEC.md`) |
| **실제** | **토스페이먼츠 실연동** — 카드 결제 + **가상계좌 발급/입금확인(폴링)** 2종 |
| **왜** | 모의 결제는 "성공 버튼 누르면 성공"이라 배울 게 거의 없다. 실제 PG를 붙여야 **결제 승인 실패 시 재고 복구**, **외부 API 응답 파싱**, **테스트에서 외부 의존을 어떻게 끊나** 같은 진짜 문제가 나온다. |
| **차이 방향** | ⬆️ **과제 요구를 초과 달성** (축소가 아님) |

**이 선택이 실제로 만들어낸 학습:**
- 외부 API를 `PaymentProcessor` **인터페이스로 감싸** 테스트에서 네트워크 없이 성공/실패 재현 (`TossPaymentProcessorTest`)
- 결제 실패 시 주문을 `CANCELED`로 되돌리고 재고 복구 — **새로고침으로 두 번 호출해도** 상태 머신이 이중 복구를 차단
- 웹훅 대신 **폴링**을 선택한 트레이드오프 (로컬 개발 시 외부에서 들어오는 웹훅을 받을 수 없음)

### A-5. 화면 구조 — 서버 렌더링 암시 → **React SPA + REST API 분리**

| | 내용 |
|---|---|
| **과제 문장** | Step 3-3: "상품 목록, 상세, 등록, 수정 등 **기본 쇼핑몰 화면과 기능**을 구현합니다" ※ 원문은 렌더링 방식을 **명시하지 않았다**. "Spring 기반 화면 구현"이라 서버 렌더링(Thymeleaf)으로 읽힐 수는 있으나, 이건 내 해석이지 원문의 요구는 아니다 |

| **대가** | 분리했더니 **각 계층은 통과인데 이어붙인 지점이 깨지는** 결함이 실제로 나왔다 → 그래서 Playwright E2E를 도입했다 (§ E2E가 따로 필요했던 이유, `FINAL_DELIVERABLE.md` §5) |

### A-요약: 심사자에게 한 문단으로 말한다면

> 과제 원문과 다르게 간 지점은 5곳입니다. 그중 **축소한 것은 하나도 없습니다.**
> 배포처(AWS→Azure)와 화면 구조(서버렌더링→SPA)는 **같은 학습 목표를 다른 경로로** 달성했고,
> 결제(모의→실제 PG)는 **요구를 초과**했으며, Vapor는 **"학습"이라는 원문 요구를 지킨 뒤 적용 범위를 판단**했습니다.
> 각 선택마다 대가와 근거를 문서에 남겼습니다.

## 2. [B] 내 문서 주장 ↔ 실제 코드 — 발견 즉시 수정한 2건

이건 정당화할 성격이 아니라 **그냥 틀린 것**이라 오늘 수정했다.

### B-1. "Vapor를 프론트 전반에 적용" → 실제 28개 중 2개 파일 ✅ 수정 완료

| | 내용 |
|---|---|
| **문서에 쓰여 있던 것** | "컴포넌트·토큰 체계를 학습해 **프론트 전반에 적용**했습니다" |
| **실제 코드** | `main.jsx`(CSS만) + `AdminPage.jsx`(컴포넌트 6개) = **2 / 28** |
| **왜 위험한가** | 심사자가 `frontend/src`를 열어보면 5초 만에 드러난다. 이 한 줄이 걸리면 **문서의 나머지 모든 수치(테스트 402개, 커버리지 98.8%)까지 의심받는다.** |
| **조치** | `FINAL_DELIVERABLE.md` **3곳 수정** — Step 1 서술, 기술 스택 표, 아키텍처 다이어그램(`Vapor DS` → `Custom CSS`) |

### B-2. "디자인 시안 = Vapor 시안"으로 읽히는 서술 ✅ 수정 완료

| | 내용 |
|---|---|
| **문서에 쓰여 있던 것** | Vapor 학습 문단 끝에 "디자인 시안 원본은 `design/` 폴더" → **Vapor 기반 시안처럼 읽힘** |
| **실제** | `design/README.md`는 "**Aesop 사이트를 벤치마킹한 미니멀·세리프 톤**"이라고 명시. 시안 파일 49KB 전체에 "vapor"라는 단어가 **0회** 등장 |
| **조치** | "디자인 방향 — Aesop 벤치마킹 자체 디자인" 항목을 분리 신설. Vapor를 관리자 화면에만 쓴 **이유와 연결**되도록 서술 |

> 💡 **여기서 배운 것:** 문서의 형용사(`전반`, `전면`, `모두`)는 **코드로 검증되는 주장**이다.
> 쓰기 전에 `grep -rl "@vapor-ui" frontend/src | wc -l` 한 줄이면 확인된다.
> 이 습관이 프로젝트의 "**git에 없으면 없는 것**" 원칙의 문서판이다.

## 3. 【집중 분석】 Step 7-3 · Step 8 — "최종 결과물 문서" 만들기

여기서부터가 **아직 안 끝난 부분**이다. 과제 원문을 한 글자씩 다시 읽는다.

> **Step 7-3.** 애플리케이션을 AWS에 배포하고 **최종 결과물(프로젝트 소개 자료)** 을 정리합니다.
> **Step 7-4.** 최종 결과물에 **배포 링크**를 첨부할 수 있는 경우 링크를 첨부합니다.
> **Step 7-5.** **시연 영상**을 준비합니다.
> **Step 8-1.** 최종 결과물 + 시연영상을 **하나의 파일로 압축**합니다.
> **Step 8-2.** 파일로 과제를 제출합니다.

### 3-1. 원문 해석 — 핵심은 괄호 안의 네 글자다

과제는 "최종 결과물"을 그냥 두지 않고 **`(프로젝트 소개 자료)`** 라고 못 박았다.
이게 이번 작업의 성격을 결정한다.

| 오해하기 쉬운 것 | 원문이 실제로 요구하는 것 |
|---|---|
| 기술 문서 / 상세 명세 | **소개 자료** — 처음 보는 사람에게 프로젝트를 **설명하는** 자료 |
| 개발자가 읽을 근거 문서 | **심사자가 읽을** 자료 |
| 길고 빠짐없는 것 | **읽히는 것** |

**그런데 지금 내 `FINAL_DELIVERABLE.md`는 486줄짜리 기술 감사 문서다.**
근거로는 훌륭하지만, "소개 자료"라는 단어에 정확히 맞는지는 따져봐야 한다. → §3-3에서 결정

### 3-2. 지금 내가 가진 문서 자산 — 3층 구조

| 층 | 파일 | 분량 | 성격 | git 추적 |
|---|---|---:|---|---|
| **① 소개층** | `document/PRESENTATION.md` | 582줄 / **29장** | 발표용 (15분 + Q&A). 스토리라인 있음 | ✅ 추적됨 |
| | `document/presentation.html` | 62KB / **32장** | 위를 HTML 슬라이드로. **디자인 토큰 적용됨** | ❌ **`.gitignore:75`로 제외** |
| **② 근거층** | `document/FINAL_DELIVERABLE.md` | 486줄 | 목표 6개 + Step 1~8 전수 대조 + 근거 링크 | ⚠️ **아직 untracked** |
| **③ 상세층** | `FUNCTIONAL_SPEC.md` · `ERD.md` · `SPRINT_PLAN.md` | — | 기능 ID·테이블 설계·일정 | ✅ 추적됨 |

**여기서 즉시 드러나는 문제 3개:**
