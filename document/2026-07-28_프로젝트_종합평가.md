> 평가 기준 커밋: `a19f273` (토스 가상계좌 결제수단 추가 병합 직후)

## 총평

CRUD만 도는 쇼핑몰이 아니라 **동시성 제어·실제 PG 연동·CI 커버리지 게이트**까지 갖춘, 부트캠프 포트폴리오 중 상위권 완성도. 다만 "코드는 잘 짰는데 배포/문서 정리가 안 끝난" 상태로, 포트폴리오로서의 마지막 마무리(라이브 링크)가 남아있다.

## 강점 (근거 파일)

- **기능 폭**: 회원/상품/장바구니/주문/결제/관리자/리뷰 — FUNCTIONAL_SPEC 계획 기능이 거의 전부 컨트롤러로 존재. 리뷰 키워드 배지(`KeywordExtractor.java`), 상품 태그 필터 등 부가 기능 포함.
- **동시성 제어**: `Product`의 `@Version`(낙관적 락) + `OrderService`의 `@Retryable`(3회, 50ms backoff). `OrderConcurrencyTest`로 검증.
- **실제 PG 연동**: 토스페이먼츠 카드+가상계좌를 실제 API(confirm/상태조회)로 연동, 실제 승인까지 브라우저 검증 완료(2026-07-28).
- **테스트 문화**: 백엔드 31개, 계층별 고른 분포, TODO/FIXME 잔재 0건.
- **CI/Docker**: 커버리지 게이트 포함 CI 2잡 병렬, 멀티스테이지 Dockerfile 2개 + docker-compose.
- **문서화**: README 로드맵·배포 체크리스트, `docs/learning/` 학습 기록.

## 면접에서 팔리는 서사 3개

1. **"결제 실패가 재고를 잠그는 문제를 어떻게 막았나"** — `pay()` 실패 시 CANCELED 전이 + 재고 복구, `canTransitionTo()`가 이중 복구를 구조적으로 차단. 상태 머신·트랜잭션·도메인 불변식이 한 줄기로 설명되는 소재.
2. **"동시 주문 시 재고 정합성"** — 낙관적 락 충돌 감지 + 재시도마다 새 트랜잭션. `@Retryable`이 `@Transactional`보다 바깥 어드바이스라는 순서 이해까지 주석으로 남김(시니어도 자주 틀리는 지점).
3. **"웹훅 대신 폴링을 택한 이유"** — 실무 표준(웹훅)과 로컬 재현성 원칙의 충돌에서 트레이드오프를 인지하고 결정. 정답 암기가 아니라 제약 하 의사결정 능력을 보여주는 소재.

## 면접에서 찔릴 지점 (사전 준비 필요)

- **"왜 JWT가 아니라 세션인가?"** — 좋은 답이 실제로 존재(단일 서버 + 같은 오리진 프록시 구조에서는 세션이 더 단순·안전, 토큰 탈취/만료 관리 문제 회피). README에 한 문단 명문화 권장.
- **`KeywordExtractor`의 사전 기반 매칭 한계** — 동의어·오탈자 한계는 주석으로 자인해뒀으나, 개선 방향(형태소 분석기 도입 등)까지 답변 준비 필요.
- **"커버리지 90%인데 어떤 버그를 테스트가 못 잡았나?"** — 완벽한 실제 사례 2개 보유:
  - 토스 `dueDate` 응답의 시간대 오프셋(`+09:00`) → `LocalDateTime` 파싱 실패 (외부 API 실응답 계약은 MockRestServiceServer로 못 잡음)
  - DB CHECK 제약조건 드리프트 — enum 값 추가 시 `ddl-auto=update`가 기존 제약조건을 갱신하지 않음 (테스트는 매번 새 H2라 구조적으로 못 잡음)

## 아쉬운 점

1. **라이브 데모 링크 없음** — 가장 큰 임팩트 손실. Docker 구성이 끝나 있어 실 작업량 반나절 수준.
2. **README 배포 체크리스트 미해결 항목** — CORS 미설정, 쿠키 HTTPS/Secure 미설정, `show-sql=true`, `ddl-auto=update`.
3. **문서-코드 불일치** — PostgreSQL 전환이 문서상 미체크이나 실제로는 이미 적용됨.
4. **`ddl-auto=update` 한계 실증** — 2026-07-28 스키마 드리프트 직접 경험. Flyway 도입 동기 확보.
5. **프론트 테스트 3개** — 백엔드 대비 불균형이나, 백엔드 중심 지원이면 우선순위 낮음.

## 우선순위 제안 (효과 대비 노력 순)

1. **라이브 배포** (Render/Fly.io 등) → README에 링크 추가. 완결성 "중"→"상"으로 올리는 최단 경로.
2. **배포 체크리스트 보안 항목 해소** — CORS·쿠키 Secure는 배포 순간 실제 장애가 되는 항목(로컬 프록시에선 안 드러남).
3. **Flyway 도입** — 스키마 드리프트를 직접 겪은 직후가 도입 최적 타이밍.
4. **README 동기화 + 세션 인증 선택 근거 명문화** — 30분 투자로 문서 신뢰도 회복.

## 핵심 교훈

- 포트폴리오 평가에서 기능 개수보다 중요한 건 **"결정의 근거가 추적 가능한가"**. 이 프로젝트는 커밋 본문·주석·체크리스트에 트레이드오프가 남아 리뷰어가 사고 과정을 재구성할 수 있다.
- "테스트 다 통과했는데 실환경에서 깨진" 경험(dueDate 파싱, CHECK 제약조건)은 테스트의 구조적 한계를 이해하는 증거로, 역설적으로 포트폴리오 가치를 올렸다.
