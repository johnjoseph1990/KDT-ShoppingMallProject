## 4. 발견한 문제: 로그인 실패인데 왜 403이었나

### 4-1. 증상

브라우저 개발자 콘솔에서 로그인 실패 요청을 보니:

```
[ERROR] Failed to load resource: the server responded with a status of 403 (Forbidden) @ /api/auth/login
```

### 4-2. 먼저 알아야 할 개념: 401 vs 403

HTTP 상태 코드는 서버가 "무슨 일이 있었는지"를 숫자로 요약해서 알려주는 약속이다. 그중 인증/인가 관련해서 자주 헷갈리는 두 개:

| 코드 | 이름 | 의미 | 이 프로젝트 예시 |
|---|---|---|---|
| **401 Unauthorized** | "너 누구인지 모르겠어" | **인증(로그인) 자체가 안 됐거나 실패함** | 로그인 시 비밀번호 틀림, 로그인 안 한 채로 `/api/auth/me` 호출 |
| **403 Forbidden** | "누군지는 알겠는데 안 돼" | **인증은 됐지만 권한이 부족함** | 일반회원(USER)이 관리자 전용 API(`/api/admin/**`) 호출 |

이름은 비슷해 보이지만 "누구인지 모름"과 "누군지는 알지만 자격 미달"은 완전히 다른 상황이라, API를 쓰는 프론트엔드나 다른 개발자가 이 코드만 보고도 원인을 구분할 수 있어야 한다. 그런데 오늘 발견한 문제는, **로그인 자체가 실패한 상황(=401이어야 함)에서 403이 나가고 있었다**는 것.

### 4-3. 왜 이런 일이 있었나 (Spring Security 흐름)

`AuthController.java`의 로그인 코드:

```java
@PostMapping("/login")
public MemberResponse login(@Valid @RequestBody LoginRequest request, ...) {
  Authentication authentication =
      authenticationManager.authenticate(
          new UsernamePasswordAuthenticationToken(request.email(), request.password()));
  // 비밀번호가 틀리면 위 authenticate()가 예외를 던진다
  ...
}
```

- `authenticationManager.authenticate(...)`는 "이 이메일+비밀번호가 실제로 맞는지" 검사하는 스프링 시큐리티의 핵심 메서드다.
- 비밀번호가 틀리면 이 메서드는 `BadCredentialsException`이라는 예외를 던진다. 이 예외는 스프링 시큐리티에서 `AuthenticationException`이라는 큰 분류에 속한다 (**"인증 자체가 실패했다"** 는 뜻).
- 이 예외를 누가 잡아서 몇 번 상태 코드로 바꿔줄지는 **`AuthenticationEntryPoint`** 라는 부품이 결정한다.
- 그런데 우리 `SecurityConfig`에는 이 부품을 따로 설정한 적이 없었다. 이럴 때 스프링 시큐리티는 자기 마음대로 기본값(`Http403ForbiddenEntryPoint`)을 쓰는데, 이건 "지정 안 하면 일단 403"이라는 **역사적으로 남아있는 기본 동작**이다. 그래서 인증 실패인데도 403이 나갔던 것.

정리하면:

```
로그인 실패
  → authenticate()가 AuthenticationException을 던짐
  → 이 예외를 처리할 AuthenticationEntryPoint가 설정 안 되어 있었음
  → 스프링 시큐리티 기본값(Http403ForbiddenEntryPoint) 적용
  → 결과: 403 (원래는 401이어야 함)
```

### 4-4. 수정 내용 (`SecurityConfig.java`)

```java
.exceptionHandling(
    exception ->
        exception.authenticationEntryPoint(new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)))
```

- `exceptionHandling(...)`: "인증/인가 실패했을 때 각각 어떻게 응답할지" 설정하는 부분.
- `authenticationEntryPoint(...)`: 그중에서도 **"인증 자체가 실패했을 때"** 쓸 부품을 지정하는 자리. 여기에 `HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)`를 넣어서 "무조건 401로 응답해라"라고 명시했다.
- `HttpStatusEntryPoint`는 스프링 시큐리티가 기본 제공하는 가장 단순한 구현체 — "그냥 이 상태 코드만 내려줘"라는 용도.

**중요:** 이 설정은 `authenticationEntryPoint`만 바꾼 것이라, **권한 부족(AccessDeniedException) 쪽은 건드리지 않았다.** 그래서 일반회원이 관리자 API를 호출하면 여전히(그리고 올바르게) 403이 나온다. 즉:

- 인증 실패(로그인 실패, 비로그인 접근) → `authenticationEntryPoint` → **401** (오늘 수정)
- 인가 실패(로그인은 했지만 권한 부족) → `accessDeniedHandler` → **403** (원래도 맞았음, 안 건드림)

### 4-5. 수정 후 재검증

백엔드를 재시작한 뒤 다시 테스트:

```
[ERROR] Failed to load resource: the server responded with a status of 401 (Unauthorized) @ /api/auth/login
```

403 → 401로 바뀐 것을 확인했고, 정상 로그인/에러 메시지 등 기존 기능은 그대로 잘 동작하는 것도 재확인했다.

## 5. 자주 하는 실수 (기억해둘 것)

**"인증 실패(401)"와 "권한 부족(403)"을 같은 걸로 착각하기 쉽다.** 둘 다 "접근이 막혔다"는 느낌이라 헷갈리지만:

- 401 = "당신이 누구인지조차 확인이 안 됨" (로그인 실패, 비로그인)
- 403 = "당신이 누구인지는 알지만, 그 사람은 이 작업을 할 자격이 없음" (권한 부족)

새로운 API를 만들다가 인증/인가 에러를 처리할 때는 항상 "지금 이게 로그인 문제인가, 권한 문제인가?"를 먼저 구분하고 코드를 짜는 습관을 들이면 좋다.
