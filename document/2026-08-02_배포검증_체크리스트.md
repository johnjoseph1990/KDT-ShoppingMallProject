### 2-3. 절대 실행 금지 (운영 DB 파괴)

- ❌ 마이페이지 → 설정 → **회원 탈퇴** (시드 계정 소멸)
- ❌ 마이페이지 → 설정 → **비밀번호 변경** (다음 세션 로그인 불가)
- ❌ 관리자 → **시드 상품 18개 삭제/가격 수정** (`TEST-` 접두사 상품만 삭제)
- ⚠️ 리뷰는 한 상품당 1인 1회 — 이미 있으면 수정/삭제 시나리오로 우회

### 2-4. 인프라 제약 (테스트 설계에 직접 영향)

1. **min-replicas 0** (frontend/backend 둘 다) → 유휴 후 첫 요청은 콜드 스타트. 워밍업이 반드시 맨 앞.
2. **backend는 internal ingress** → 외부에서 직접 호출 불가. 모든 검증은 `https://<frontend>/api/...` 경유.
3. **`/actuator/health`는 nginx가 프록시하지 않음** → 외부 헬스체크 불가. `GET /api/products`를 헬스 프로브로 사용.
4. **세션은 인메모리** → 컨테이너 재기동 시 로그인이 풀린다. 테스트 중 갑자기 401이 뜨면 이걸 의심.
5. 테스트 중 **5분 이상 유휴 금지** — 사람 입력을 기다리는 구간 전후로 `fetch('/api/products?size=1')` 핑.

#### 결제 실패 → 원인 즉시 판별 (핵심 진단표)

| 증상 | 원인 |
|---|---|
| `alert("결제 키가 설정되지 않았습니다...")` — 결제창 자체가 안 열림 | **`VITE_TOSS_CLIENT_KEY` 누락** (GitHub Secret → Docker build-arg) |
| 결제창은 뜨는데 주문이 **"취소됨"** | **`TOSS_SECRET_KEY` 누락/오류** — 토스 401 → `ConfirmResult.failed()` → CANCELED + 재고 복구. **HTTP는 200이라 에러로 안 보인다** |
| "결제 승인 처리 중 문제가 발생했습니다" | `POST /orders/{id}/pay`가 4xx/5xx (금액 불일치 or 백엔드 예외) |
| 토스가 "잘못된 클라이언트 키" 표시 | 두 키가 서로 다른 상점의 키 (짝 불일치) |

#### 카드 결제 절차 (사람 개입 지점)

1. **[자동]** `/orders/{B}` → 카드 라디오 → "결제하기" → `browser_tabs(list)`로 새 탭/팝업 여부 실측 → 스냅샷
2. **[분기]**
   - (a) 결제창에 "결제하기" 버튼만 → 그대로 클릭, 완전 자동
   - (b) 카드번호 입력 화면 → 일반 `<input>`이면 자동 입력 시도. **보안 키패드(canvas/iframe)면 자동화 불가 → 사람에게 hand-off**
   - (c) 결제창이 아예 안 뜸 → 위 진단표로 판정 후 §S4-4 우회로
3. **[자동]** 원래 탭으로 복귀 → `/payments/success` → `/orders/{B}` → 상태 `결제완료` 확인

> hand-off 대기 중에는 **백엔드 재수면 방지 핑**을 걸 것.

#### S4-4. PAID 도달 실패 시 우회로 (S6 언블록 전용)

관리자 → 주문관리 → 주문 B를 `결제완료`로 변경 (`ORDERED → PAID` 전이는 허용됨).

## 5. 실패 시 원인 切り分け — 4계층 진단

```
증상 발생
 ├─ ① 화면이 안 뜬다
 │    ├─ JS 번들 404        → 프론트 이미지 빌드 실패 (레이어: 빌드/CD)
 │    └─ JS 에러            → 프론트 코드 버그 (레이어: 프론트)
 │
 ├─ ② API 실패 → 상태코드로 분기
 │    ├─ Content-Type이 text/html (JSON 기대) → nginx가 /api를 프록시 안 하고 SPA fallback
 │    │                                        (레이어: nginx / BACKEND_URL 미주입 / 구버전 이미지)
 │    ├─ 502·504  → nginx는 살아있고 백엔드 도달 실패 (콜드스타트 or 내부 DNS)
 │    ├─ 401      → /api/auth/* 면 정상. 그 외면 세션 소실 (컨테이너 재기동 의심)
 │    ├─ 403      → 인가. 의도된 동작일 수도 (S5-3, S8-4)
 │    ├─ 500      → /api/products가 되면 DB 정상 → 로직 문제
 │    │             /api/products도 500 → DB 연결/스키마 문제
 │    └─ 200인데 데이터 이상 → 시드 미실행 or 이전 테스트 잔여물
 │
 └─ ③ 결제 실패 → §Phase 4 진단표
```

**레이어 확정용 3-핑** (증상이 애매할 때 한 번에):
```js
async () => {
  const probe = async (u, o) => {
    try { const r = await fetch(u, o); return { u, s: r.status, ct: r.headers.get('content-type') }; }
    catch (e) { return { u, err: e.message }; }
  };
  return [
    await probe('/index.html'),                               // ① nginx 정적
    await probe('/api/products?size=1'),                      // ② nginx→백엔드→DB
    await probe('/api/auth/me', { credentials: 'include' }),  // ③ 세션
  ];
}
```
- ①만 성공 → nginx 프록시 문제
- ①② 성공 / ③ 401 → 세션 문제
- 전부 성공인데 화면이 깨짐 → 프론트 렌더링 문제

### DEF-10 상세 — nginx 캐시 헤더 (커밋 `58526f9`)

**원인**: `frontend/nginx.conf`의 `location /` (SPA fallback 포함)에 캐시 헤더가 전혀 없어 브라우저 기본 정책에 맡겨져 있었다. `/assets/*.js|css`는 Vite가 콘텐츠 해시를 파일명에 붙이므로 내용이 바뀌면 파일명도 바뀌어 영구 캐시해도 안전한데, `index.html`은 해시 없는 고정 파일명이라 정반대로 가야 했다.

**수정**:
```nginx
location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}
location = /index.html {
    add_header Cache-Control "no-cache";  # 저장은 하되 매번 재검증(ETag로 304 가능)
}
```

**검증 방법** (Azure 배포 전, 로컬에서 실제 이미지로):
1. `envsubst`로 템플릿 치환 후 `docker run nginx:alpine nginx -t` — 문법 검증
2. `docker build`로 실제 프론트 이미지 생성 (CRLF 이슈로 커스텀 entrypoint 대신 `docker-entrypoint.d/20-envsubst-on-templates.sh` 직접 실행 후 `nginx -g 'daemon off;'`로 우회 실행)
3. `curl -I`로 세 경로 확인 — `index.html`·`/orders`(SPA 딥링크, try_files 내부 리다이렉트 경유)·`/assets/*.js` 모두 의도한 `Cache-Control` 확인

### DEF-2 상세 — 백엔드에 배송비 도입 (커밋 `002c1cb`)

**원인**: 배송비 개념 자체가 백엔드에 없었다. `Order` 엔티티에 필드 없음, `OrderService.createOrder()`는 상품가 합계만 계산, `pay()`의 결제 금액 검증도 상품가만 비교. 프론트(`CartPage.jsx`)만 독자적으로 배송비를 계산해 "N원 결제하기" 버튼에 표시했지만, 실제 `POST /orders` 요청에는 그 값을 싣지 않았다.

**수정**:
- `Order.java`에 `FREE_SHIPPING_THRESHOLD`(40,000원)/`SHIPPING_FEE`(3,500원) 상수, `shippingFee` 필드(주문 시점 스냅샷), `applyShippingFee()` — 상품을 모두 담은 뒤(장바구니 전체 합계 기준으로) 호출

- `pay()`의 결제 금액 검증과 프론트의 토스 결제 요청 금액(`amount: order.totalPrice`)은 **코드 변경 없이 자동으로 정합성이 맞음** — `totalPrice`가 이제 배송비를 포함하기 때문
- `OrderDetailPage.jsx`에 "배송비" 줄 추가 — "상품금액 + 배송비 = 합계" 형태로 표시

**원인**: `ProductService.findBestProducts()`의 3단계 폴백(REVIEW_BEST→SALES→LATEST)이 "앞 단계가 하나라도 결과를 내면 그걸로 전량 확정"하는 배타적 전환이었다. 전환 임계값이 코드에도 테스트에도 없었고, 오히려 "판매 실적 상품 1개만 있어도 SALES 전환"이 기존 테스트에 정상 명세로 박혀 있었다.

**수정**: 각 단계가 앞 단계가 요청 개수(size=5)를 못 채운 만큼만 다음 단계로 넘어가 REVIEW_BEST+SALES+LATEST를 섞어서라도 최대한 채운다. `LinkedHashMap`(상품 id 키)으로 여러 단계 후보에 겹치는 상품의 중복을 제거하면서 먼저 뽑힌 우선순위를 유지. 화면 상단 배지는 목록 첫 항목의 source를 그대로 쓰므로 "가장 강한 근거가 대표로 노출"되는 기존 의미는 유지된다.

프론트(`HomePage.jsx`)도 방어적으로 손봤다 — 그리드 컨테이너의 회색 배경(gap 경계선 용도)이 빈 칸에 비치는 문제를 막기 위해 데스크톱 열 수를 실제 카드 개수에 맞춤(모바일은 `!important` 규칙이 그대로 2열 강제라 영향 없음).

**검증**: TDD로 기존 3개 테스트에 후속 단계 stub 추가(NPE 방지) + 채우기 동작 자체를 검증하는 신규 테스트 2개(판매1+최신3 채우기, 여러 단계 중복 상품 처리) → 전체 27개 통과. 로컬 Docker 재배포 후 API 확인(로컬은 판매 실적이 이미 다양해 SALES만으로 5개 채워짐).

### DEF-5 상세 — 죽어 있던 업로드 경로를 화면에 연결

**원인**: 백엔드는 완성돼 있었다. `UploadController`(`POST /api/admin/upload`) → `AzureBlobService` → Azure Blob까지 전부 정상이고, S8-2에서 JS로 직접 호출했을 때 200 + 공개 URL을 받았다. 빠진 건 **화면 하나**였다 — AdminPage 상품 폼에 `<input type="file">`이 없어서 `frontend/src/api/admin.js`의 `uploadImage()`가 어디서도 import되지 않는 dead code로 남아 있었다. 관리자는 이미지 URL을 손으로 타이핑하는 수밖에 없었다.

**수정**:
- `frontend/src/utils/imageUpload.js` 신규 — 검증 규칙과 에러 문구를 컴포넌트 밖 순수 함수로 분리
  - `validateImageFile(file)` — **타입을 크기보다 먼저** 검사한다. PDF를 고른 사용자에게 "10MB 이하만 됩니다"라고 하면 압축이라는 엉뚱한 행동을 유도하게 된다. 크기 초과 시에는 한계값과 실제 크기를 함께 준다(`10MB 이하만 업로드할 수 있습니다. (선택한 파일: 23.4MB)`). 예외를 던지지 않고 **에러 문구를 값으로 반환**(정상이면 `null`)해 호출부가 try/catch 없이 분기한다
  - `uploadErrorMessage(err)` — 503(Azure 환경변수 미주입)/403(권한)/413(서버 크기 거부)을 서로 다른 문구로 구분. DEF-1이 "취소됨" 한 마디로만 보여 원인 파악이 늦어졌던 것과 같은 실수를 피하기 위함
- `AdminPage.jsx` — 파일 선택 → 검증 → 업로드 → 받은 URL을 `imageUrl` 칸에 자동 입력. 업로드 중에는 파일 입력과 저장 버튼을 잠가(`uploading`) URL이 비어 있는 채로 상품이 저장되는 것을 막고, 에러는 `role="alert"`로, 결과는 썸네일 미리보기로 표시. URL 직접 입력 방식도 그대로 남겨둠

**설계 판단 2가지**:
1. `MAX_IMAGE_SIZE_BYTES`를 백엔드 `spring.servlet.multipart.max-file-size`(10MB)와 **같은 값으로 맞추고 그 계약을 테스트로 못 박았다**. 프론트가 더 관대하면 사용자는 업로드를 다 기다린 뒤 413을 맞고, 더 엄격하면 서버가 받을 수 있는 파일을 괜히 막는다.
2. `await` 뒤의 `setForm`은 **함수형 업데이트**(`setForm(prev => ...)`)로 썼다. 업로드를 기다리는 동안 사용자가 상품명 등 다른 칸을 고칠 수 있는데, `{...form}`을 쓰면 오래된 스냅샷으로 덮어써서 그 입력이 사라진다.

**검증**: `imageUpload.test.js` 15개 신규(경계값 10MB 정확히/1바이트 초과, 타입-크기 동시 위반 시 순서, `file.type`이 빈 문자열인 경우, 에러 매핑 5종) → 프론트 전체 45개 통과. `npm run build` 통과.

```
az containerapp secret list --name backend -g mins-shopping-rg --query "[].name"
# azure-storage-conn, pg-password, toss-secret-key  ← 모두 존재
```
