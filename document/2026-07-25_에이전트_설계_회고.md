# 에이전트 설계 회고·발표 메모 (2026-07-25)

> 목적: 왜 서브에이전트를 이렇게 설계했는지, 회고·발표 때 꺼내 쓸 핵심만 정리.
> (초안 — 나중에 살 붙일 예정. 지금은 뼈대만.)

## 1. 왜 만들었나 (문제의식)
- CLAUDE.md 하나에 여러 역할(요구사항·보안·품질·학습주석·테스트)이 뒤섞여 있었음 → 실패 모드가 서로 달라 한 세션이 다 맡으면 놓침이 생김.
- 목표 상향: **부트캠프 제출물 → 실서비스 운영 수준**. 검토 기준이 "맞고 깔끔한가" → "24시간·실제 돈이 오가면 뭐가 터지나"로 바뀜.

## 2. 설계 원칙 3가지
1. **결정론적 검사는 Hook, 판단은 LLM** — 테스트 통과·포맷은 실행(검증), 설계 좋고 나쁨은 에이전트(리뷰).
2. **실패 모드가 다르면 에이전트를 분리** — 컨벤션 위반 vs 돈 유실은 다른 문제 → 다른 에이전트.
3. **읽기전용은 병렬, 쓰기는 단독** — 권한 분리가 병렬화의 전제(파일 충돌 방지).

## 3. 에이전트 6종 구성
| 에이전트 | 역할 | 권한/모델 |
|---|---|---|
| spec-reviewer | 요구사항 방향 | 읽기전용 / sonnet |
| security-reviewer | OWASP 보안 | 읽기전용 / sonnet |
| code-reviewer | 컨벤션·설계 | 읽기전용 / sonnet |
| learning-annotator | 학습 주석(완화: 개념 첫 등장만) | 읽기전용 / haiku |
| test-writer | 테스트 작성+실행(검증) | 쓰기 / inherit |
| reliability-reviewer | 운영 신뢰성(결제 멱등성 등) | 읽기전용 / sonnet |

## 4. 학습 → 운영 진화
- 신규 `reliability-reviewer` 추가: 멱등성·트랜잭션 경계·부분 실패·재시도·동시성. 돈 걸린 결제/주문이 1순위 공백이라 여기부터.
- `learning-annotator` 완화: 라인마다 → 개념 처음 등장할 때만 (운영 코드는 자기설명적이 원칙).
- 남은 층(다음 단계): 데이터 안전성(Flyway), 관측성, 성능.

## 5. 회고 포인트 (초안)
- 잘한 점: 역할 분리로 리뷰 관점이 선명해짐 / 권한 분리로 병렬 안전성 확보.
- 아쉬운 점: Hook(커밋 전 포맷 강제) 미구축 / 게이팅 정책 일부 미정(TODO).
- 다음: reliability-reviewer 게이팅 정책 확정 → 운영 3대 영역 순차 도입.

## 6. 발표 talking points (한 줄씩)
- "AI 리뷰어를 역할별로 쪼갠 이유 = 실패 모드가 다르기 때문."
- "리뷰(판단) vs 검증(사실)을 분리 — code-reviewer는 실행 안 함, test-writer만 실행."
- "학습 프로젝트를 운영 수준으로 끌어올리는 첫 삽 = 결제 멱등성 검토."
