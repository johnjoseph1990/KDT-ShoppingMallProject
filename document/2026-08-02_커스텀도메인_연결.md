## 1. 배경 지식 — 도메인이 내 사이트로 연결되는 원리

### 1-1. DNS는 "이름 → 주소" 전화번호부다

브라우저에 `www.minsdev.works`를 치면 실제 통신은 IP 주소로 이뤄진다.
이름을 IP로 바꿔주는 시스템이 **DNS(Domain Name System)** 다.

```
브라우저 → "www.minsdev.works 어디야?" → DNS → "4.230.67.122야" → 그 IP로 접속
```

### 1-2. 등록기관(Name.com)이 "전화번호부 페이지"를 준다

도메인을 사면 등록기관이 그 도메인의 **DNS 레코드**를 편집할 권한을 준다.
여기에 "이 이름은 저기로 보내라"를 적어두는 것이 도메인 연결 작업의 전부다.

### 1-3. 이번에 쓴 레코드 3종류

| 타입 | 하는 일 | 이번 용도 |
|---|---|---|
| **A** | 이름 → **IP 주소** | 루트 도메인을 Azure 환경 고정 IP로 |
| **CNAME** | 이름 → **다른 이름**(별칭) | `www`를 Azure가 준 긴 FQDN으로 |
| **TXT** | 이름 → **임의의 문자열** | 도메인 소유권 증명 |

### 1-4. 왜 루트는 A인데 www는 CNAME인가? (중요)

DNS 표준(RFC 1034)상 **루트 도메인에는 CNAME을 쓸 수 없다.**

- CNAME은 "이 이름의 **다른 모든 레코드를 대체한다**"는 의미다.
- 그런데 루트 도메인(`minsdev.works`)에는 NS·SOA 레코드가 **필수로** 있어야 한다.
- 둘이 충돌하므로 루트에는 CNAME 금지 → **IP를 직접 적는 A 레코드**를 쓴다.

반면 `www.minsdev.works`는 그냥 하위 이름이라 제약이 없어 CNAME이 가능하다.
CNAME이 더 좋은 이유: Azure가 나중에 IP를 바꿔도 **자동으로 따라간다**(이름을 가리키므로).
A 레코드는 IP가 바뀌면 손으로 고쳐야 한다.

> **그럼 A 레코드에 박은 IP는 안 바뀌나?**
> Container Apps는 **환경(`mins-shopping-env`) 단위로 IP가 고정**된다.
> 앱을 몇 번 재배포해도 그대로다. 단 **환경 자체를 삭제하고 다시 만들면 바뀐다** — 그때는 A 레코드도 고쳐야 한다.

### 1-5. `asuid` TXT 레코드 = 소유권 증명

Azure는 "이 도메인이 정말 당신 것인가"를 확인한다. 없으면 남의 도메인을 내 앱에 붙여
피싱 사이트를 만들 수 있기 때문이다.

방법: Azure가 랜덤 문자열(검증 ID)을 알려주고, 그걸 DNS에 넣게 한다.
**DNS에 값을 넣을 수 있다 = 그 도메인의 관리 권한이 있다**는 증명이 된다.

```bash
# 검증 ID는 언제든 원본에서 다시 조회할 수 있다 (채팅 기록 뒤지지 말 것)
az containerapp show -n frontend -g mins-shopping-rg \
  --query "properties.customDomainVerificationId" -o tsv
```

이 ID는 **도메인이 아니라 Container App 단위**로 발급된다.
그래서 `minsdev.works`와 `www.minsdev.works`가 **같은 값**을 쓴다 (둘 다 `frontend` 앱에 붙으므로).

## 2. 실제로 등록한 DNS 레코드 4개

Name.com → `minsdev.works` → DNS Records 화면:

| # | Type | Host | Value | 의미 |
|---|---|---|---|---|
| 1 | `A` | `@` (빈칸) | `4.230.67.122` | 루트 → Azure 환경 고정 IP |
| 2 | `TXT` | `asuid` | `DDAE62...212A82` (64자) | 루트 도메인 소유권 증명 |
| 3 | `CNAME` | `www` | `frontend.agreeableisland-659b2709.koreacentral.azurecontainerapps.io` | www → Azure 프론트 FQDN |
| 4 | `TXT` | `asuid.www` | `DDAE62...212A82` (64자, 2번과 동일) | www 소유권 증명 |
**최종적으로 필요한 레코드는 이 4개가 전부다.**
(루트 인증서 검증용 `_dnsauth` TXT를 한때 추가하려 했으나, HTTP 검증으로 전환해 불필요해졌다 — 3-5 참고)

- 기존에 있던 Name.com **주차 페이지 A 레코드(`91.195.240.94`)는 삭제**했다.
- TTL은 300초(5분)로 낮게 잡았다 → 잘못 넣어도 빨리 고칠 수 있다. 안정화 후 3600으로 올려도 된다.

### TXT 레코드가 두 종류인 이유 (혼동 주의)

이름이 비슷해서 헷갈리지만 **서로 다른 두 층의 증명**이다.

| 단계 | 누가 확인하나 | 무엇을 증명하나 | 이번에 쓴 방법 |
|---|---|---|---|
| **호스트명 등록** | **Azure** | "이 도메인을 내 앱에 붙일 권한이 있다" | `asuid` / `asuid.www` TXT |
| **인증서 발급** | **인증기관(CA)** | "이 도메인을 제어한다" | www→CNAME 검증, 루트→**HTTP 검증** |

Azure에게 증명하는 것과, 실제로 인증서를 발급해주는 CA에게 증명하는 것은 별개다.
HTTPS 인증서는 아무나 남의 도메인 이름으로 발급받으면 안 되기 때문이다.
그래서 `asuid` TXT를 넣었다고 인증서까지 자동으로 나오지는 않는다.

## 3. Azure 쪽 작업

### 3-1. 인프라 정보 조회

```bash
# 환경 고정 IP (A 레코드에 넣을 값)
az containerapp env show -n mins-shopping-env -g mins-shopping-rg \
  --query "properties.staticIp" -o tsv
# → 4.230.67.122

# 프론트엔드 FQDN (CNAME에 넣을 값)
az containerapp show -n frontend -g mins-shopping-rg \
  --query "properties.configuration.ingress.fqdn" -o tsv
# → frontend.agreeableisland-659b2709.koreacentral.azurecontainerapps.io

# 소유권 검증 ID (TXT에 넣을 값)
az containerapp show -n frontend -g mins-shopping-rg \
  --query "properties.customDomainVerificationId" -o tsv
```

### 3-2. 호스트명 등록 → 인증서 바인딩 (순서 중요)

한 번에 `bind`만 하면 실패한다. **먼저 `add`로 호스트명을 등록해야** 인증서를 만들 수 있다.

```
ERROR: (RequireCustomHostnameInEnvironment) Creating managed certificate requires
hostname 'www.minsdev.works' added as a custom hostname to a container app...
```

올바른 순서:

```bash
# ① 호스트명 등록 (이 단계에서는 bindingType=Disabled — 아직 인증서 없음)
az containerapp hostname add \
  --name frontend --resource-group mins-shopping-rg \
  --hostname www.minsdev.works

# ② 관리형 인증서 발급 + 바인딩 (bindingType=SniEnabled 로 바뀜)
az containerapp hostname bind \
  --name frontend --resource-group mins-shopping-rg \
  --hostname www.minsdev.works \
  --environment mins-shopping-env \
  --validation-method CNAME
```

루트 도메인도 똑같이 하되 **검증 방식만 다르다**:

```bash
az containerapp hostname add -n frontend -g mins-shopping-rg --hostname minsdev.works
az containerapp hostname bind -n frontend -g mins-shopping-rg --hostname minsdev.works \
  --environment mins-shopping-env --validation-method TXT   # ← CNAME 아니라 TXT
```

### 3-3. 왜 검증 방식이 다른가?

| 호스트 | DNS 레코드 | 검증 방식 | 이유 |
|---|---|---|---|
| `www` | CNAME | `CNAME` | www의 CNAME이 이미 Azure FQDN을 가리키므로, CA가 DNS 체인만 따라가서 "이 이름은 Azure가 제어한다"를 확인 가능 → **추가 레코드 불필요** |
| 루트 | A | `TXT` | A 레코드의 IP는 환경 내 모든 앱이 공유하는 값이라 IP만으론 판단 불가 → **`_dnsauth` TXT에 토큰을 넣어** 증명 |

### 3-5. TXT 검증에서 막혀 HTTP 검증으로 전환한 이야기 (실제 겪은 일)

**처음엔 `--validation-method TXT`로 시도했다.** 그런데 인증서가 `Pending` 상태로 멈춘 채
**에러도 없이** 계속 기다렸다. `error: null`이라 "그냥 오래 걸리나?"로 오해하기 쉬웠다.

리소스 전체를 덤프해보니 원인이 나왔다 — **검증 토큰을 DNS에 넣어달라고 기다리는 중**이었다.

```bash
az containerapp env certificate list -n mins-shopping-env -g mins-shopping-rg \
  --managed-certificates-only -o json
# properties.validationToken: "_r9h0uyh9n52z73d36sjif03rmepr71c"  ← 이 필드가 있었다
```

TXT 방식은 이 토큰을 **`_dnsauth.<도메인>`** TXT 레코드로 등록해야 진행된다.
그런데 이 레코드 등록이 계속 실패했고(저장이 안 됨), 결국 검증 시간이 만료되어 바인딩이 실패했다.

```
ERROR: (CertificateProvisioningError) Certificate 'mc-mins-shopping--minsdev-works-3144'
       is not in succeeded provisioning state.
```

**해결: HTTP 검증으로 전환.** DNS 레코드가 아예 필요 없는 방법이다.

```bash
# ① 멈춘 Pending 인증서 삭제 (바인딩 안 된 상태라 서비스 영향 없음)
az containerapp env certificate delete -n mins-shopping-env -g mins-shopping-rg \
  --certificate mc-mins-shopping--minsdev-works-3144 --yes

# ② HTTP 검증으로 재발급
az containerapp hostname bind -n frontend -g mins-shopping-rg \
  --hostname minsdev.works --environment mins-shopping-env \
  --validation-method HTTP
```

### 3-6. 세 가지 검증 방식 비교

| 방식 | 원리 | 추가 DNS 레코드 | 언제 쓰나 |
|---|---|---|---|
| `CNAME` | 그 이름의 CNAME이 Azure FQDN을 가리키는지 DNS 체인으로 확인 | 불필요 | **서브도메인**(www 등). CNAME이 이미 있으므로 |
| `TXT` | Azure가 준 토큰을 `_dnsauth.<도메인>` TXT에 넣어 확인 | **필요** (`_dnsauth`) | 루트 도메인. 다만 레코드 하나를 더 관리해야 함 |
| `HTTP` | CA가 `http://<도메인>/.well-known/...`으로 **직접 접속**해 응답 확인 | 불필요 | 루트 도메인. **A 레코드가 이미 Azure를 가리키고 호스트명이 등록돼 있으면 이게 제일 간단** |

**루트 도메인에 HTTP 검증이 통하는 이유:** A 레코드가 환경 고정 IP를 가리키고
`minsdev.works`가 `frontend` 앱의 커스텀 호스트명으로 이미 등록되어 있어서,
Azure ingress가 이 도메인 요청을 받을 준비가 끝나 있다.
즉 **"이 주소로 오는 요청에 응답할 수 있다 = 이 도메인을 제어한다"** 가 성립한다.

> **진단 요령:** `Pending`이 오래 가고 `error`가 `null`이면 대개 "무언가를 기다리는 중"이다.
> `-o table`로는 안 보이는 필드(`validationToken` 등)가 원인을 쥐고 있을 수 있으니
> **`-o json`으로 리소스 전체를 덤프해서 보라.**

### 3-4. 인증서

- **Azure 관리형 인증서(Managed Certificate)** — 무료, 만료 전 자동 갱신. 따로 관리할 게 없다.
- 호스트명 **하나당 인증서 한 장**. 와일드카드(`*.minsdev.works`)는 지원하지 않는다.
  → `minsdev.works`용, `www.minsdev.works`용 **총 2장**이 발급됐다.
- 발급에 수 분~최대 20분 걸린다. 진행 중에는 상태가 `Pending`이다.

```bash
# 바인딩 상태 확인 (Disabled = 인증서 없음, SniEnabled = 정상)
az containerapp show -n frontend -g mins-shopping-rg \
  --query "properties.configuration.ingress.customDomains[].{name:name, binding:bindingType}" -o table

# 인증서 발급 상태 확인 (Pending → Succeeded)
az containerapp env certificate list -n mins-shopping-env -g mins-shopping-rg \
  --managed-certificates-only \
  --query "[].{name:name, subject:properties.subjectName, state:properties.provisioningState}" -o table
```

## 4. 코드 변경 — 루트 → www 301 리다이렉트

### 4-1. 왜 필요한가

`minsdev.works`와 `www.minsdev.works` **둘 다 붙여놨기 때문에**, 아무 처리도 안 하면
같은 사이트가 서로 다른 두 주소로 존재하게 된다. 문제는 두 가지:

1. **SEO** — 검색엔진이 중복 콘텐츠로 보고 평가를 두 주소에 나눠 준다.
2. **세션 쿠키** — 쿠키는 도메인별로 저장된다. `minsdev.works`에서 로그인하고
   `www.minsdev.works`로 이동하면 **로그인이 풀린 것처럼 보인다.**
   (이 프로젝트는 세션 쿠키 기반 인증이라 실제로 겪을 수 있는 문제다)

그래서 하나를 **정본(canonical)** 으로 정하고 나머지는 그쪽으로 넘긴다.

### 4-2. `frontend/nginx.conf`에 추가한 내용

```nginx
server {
    listen 80;
    server_name minsdev.works;          # Host 헤더가 정확히 이 값일 때만 이 블록 선택

    return 301 https://www.minsdev.works$request_uri;
}

server {
    listen 80 default_server;           # 나머지 전부 (www, Azure FQDN, 헬스체크...)
    ...기존 내용...
}
```

### 4-3. 세 가지 판단 포인트

**① 301 vs 302**
- `301` = 영구 이동. 검색엔진이 색인을 www로 옮기고, 브라우저가 강하게 캐시한다.
- `302` = 임시. 캐시 안 되어 되돌리기 쉽지만 SEO 이점이 없다.
- → "www를 계속 정본으로 간다"는 결정이 확고하므로 **301** 선택.

**② 목적지 스킴에 `$scheme`을 쓰면 안 되는 이유 (핵심 함정)**

Azure Container Apps는 **앞단 프록시(Envoy)에서 TLS를 종료**하고,
컨테이너로는 **평문 HTTP**로 넘긴다. 즉 nginx 안에서 `$scheme`은 HTTPS 접속이어도 항상 `http`다.

```nginx
return 301 $scheme://www.minsdev.works$request_uri;   # ❌ HTTPS 접속자를 http로 되돌려보냄
return 301 https://www.minsdev.works$request_uri;     # ✅
```

> 이건 **프록시 뒤에 있는 앱이 자기 위치를 착각하는** 고전적 버그 계열이다.
> 같은 뿌리의 증상들: Spring Security가 `http://`로 리다이렉트해 로그인 루프에 빠짐,
> 이메일 링크가 `http`로 생성됨, 쿠키 `Secure` 플래그가 안 붙음.
> 해법도 같은 계열: 앞단이 붙여주는 `X-Forwarded-*` 헤더를 신뢰하거나
> (Spring은 `server.forward-headers-strategy=framework`), 지금처럼 확정된 값을 박거나.

**③ `$request_uri`로 경로 보존**

`$request_uri`는 쿼리스트링까지 포함한 원래 경로(`/products/3?sort=new`)다.
이게 없으면 `minsdev.works/products/3`으로 들어온 사람이 홈으로 튕긴다.

### 4-4. `default_server`를 명시한 이유

server 블록이 하나뿐일 때는 자동으로 기본값이었다. 블록이 둘이 되었으므로
"위 블록과 Host가 안 맞는 나머지 요청은 여기로"를 명시해야 한다.

> 중복 걱정 안 해도 되는 이유: 이 템플릿은 `/etc/nginx/conf.d/default.conf`로 출력되어
> 기본 이미지의 동명 파일을 **덮어쓴다**. `duplicate default server` 에러가 나지 않는다.

## 5. 프론트엔드 코드는 왜 안 고쳐도 됐나

도메인이 바뀌어도 수정이 필요 없게 이미 짜여 있었다.

| 위치 | 코드 | 왜 안전한가 |
|---|---|---|
| `frontend/src/api/axiosInstance.js` | `baseURL: '/api'` | **상대경로**라 어느 도메인에서 열든 그 도메인의 `/api`로 간다 |
| `frontend/src/pages/OrderDetailPage.jsx` | `successUrl: ${window.location.origin}/payments/success` | 토스 결제 후 돌아올 주소를 **현재 접속한 도메인** 기준으로 계산 |
| 백엔드 CORS | 설정 자체가 없음 | nginx가 `/api`를 프록시해서 브라우저 입장에선 **같은 오리진** → CORS 미발생 |

> 만약 `baseURL`에 `https://frontend.xxx.azurecontainerapps.io/api`처럼 절대경로를 박았다면,
> 도메인 바꿀 때마다 프론트를 재빌드해야 했다. **상대경로가 이런 상황에서 값을 한다.**

## 6. 트러블슈팅 기록 — DNS 값이 3번 잘렸던 일

### 무슨 일이 있었나

레코드 4개를 등록한 뒤 검증했더니 3개가 틀려 있었다. 전부 **"문자 누락"** 패턴이었다.

| 레코드 | 등록된 값 | 문제 |
|---|---|---|
| A `@` | `4.230.67.12` | 맨 끝 `2` 누락 |
| CNAME `www` | `...agreeableisland659b2709...` | **하이픈(`-`) 누락** |
| TXT `asuid` | 55자 → (수정 후) 60자 | 64자여야 하는데 계속 잘림 |

`asuid` TXT는 세 번을 고쳐서야 맞았다. 두 번째 시도는 **저장 자체가 안 됐다**(값이 그대로였음).

### 왜 이런 게 위험한가

`4.230.67.12`는 **유효한 IP 형식**이다. DNS는 아무 에러 없이 받아준다.
문법은 맞고 의미만 틀린 값이라, 나중에 "왜 사이트가 안 뜨지?"로만 나타난다.

특히 64자 무의미 hex 문자열(`asuid` 값)은 **사람이 눈으로 검증할 수 없는 유일한 값**이다.
IP나 FQDN은 틀리면 "어? 하이픈 없네"가 보이지만 hex는 안 보인다.
→ **길이 체크나 자동 비교로만** 잡힌다.

> 실무에서 API 키·시크릿을 손으로 옮기지 않고 CLI/시크릿 매니저로 주입하는 이유가 같다.
> 이 프로젝트 `.github/workflows/ci.yml`의 "Verify deploy secrets" 스텝도 같은 발상 —
> **사람이 못 보는 값은 기계가 검사한다.**

### 진단의 핵심: 권한 네임서버 vs 캐시 리졸버

이 구분을 모르면 "기다리면 되겠지"로 몇 시간을 날린다.

| 구분 | 예시 | 역할 |
|---|---|---|
| **캐시 리졸버** | `1.1.1.1`, `8.8.8.8` | 남의 답을 TTL 동안 보관해 알려주는 **중개상** |
| **권한 네임서버** | `ns1psw.name.com` | 값을 실제로 소유한 **원본** |

- 원본이 옛 값 → **등록이 안 된 것** (기다려도 소용없음)
- 원본은 새 값인데 중개상만 옛 값 → **캐시 문제** (TTL만큼 기다리면 됨)

실제로 두 번째 시도 때 "캐시겠지" 하고 넘어갈 뻔했는데,
권한 네임서버에 직접 물어보니 원본 자체가 옛 값이어서 저장 실패를 잡아냈다.

## 7. 검증 방법 (재현 가능)

### 7-1. DNS 레코드 4개 일괄 검증 (PowerShell)

```powershell
$expectId    = "DDAE62BD0994D2267A71C379B9500AF712E6CDEC17D1A871B1384AF2ED212A82"
$expectIp    = "4.230.67.122"
$expectCname = "frontend.agreeableisland-659b2709.koreacentral.azurecontainerapps.io"

# 권한 네임서버(캐시 우회)와 캐시 리졸버를 모두 확인
foreach ($srv in @('ns1psw.name.com','1.1.1.1','8.8.8.8')) {
  "--- $srv ---"
  $a  = (Resolve-DnsName minsdev.works          -Type A     -Server $srv | ? {$_.Type -eq 'A'}).IPAddress
  $t1 = (Resolve-DnsName asuid.minsdev.works    -Type TXT   -Server $srv).Strings -join ''
  $c  = (Resolve-DnsName www.minsdev.works      -Type CNAME -Server $srv | ? {$_.Type -eq 'CNAME'}).NameHost
  $t2 = (Resolve-DnsName asuid.www.minsdev.works -Type TXT  -Server $srv).Strings -join ''
  "A(apex)         MATCH=$($a  -eq $expectIp)    '$a'"
  "TXT(asuid)      MATCH=$($t1 -eq $expectId)    len=$($t1.Length)"   # ← 길이 체크가 핵심
  "CNAME(www)      MATCH=$($c  -eq $expectCname) '$c'"
  "TXT(asuid.www)  MATCH=$($t2 -eq $expectId)    len=$($t2.Length)"
}
```

## 8. 앞으로 알아둘 것

| 상황 | 조치 |
|---|---|
| 인증서 만료 | **자동 갱신** — 할 일 없음 |
| Container Apps **환경을 삭제/재생성** | 고정 IP가 바뀜 → A 레코드 수정 필요 |
| 프론트 앱만 재배포 | FQDN·IP 안 바뀜 → **DNS 건드릴 필요 없음** |
| 정본을 루트로 바꾸고 싶어짐 | nginx의 `server_name`/`return` 방향을 반대로. 단 301은 브라우저가 캐시하므로 전환이 느리게 보일 수 있음 |
| 토스페이먼츠 | `successUrl`이 `window.location.origin` 기반이라 자동 대응. **단 라이브 키 전환 시엔 토스 상점 설정에 새 도메인 등록이 필요할 수 있음** |
| 하위 도메인 추가 (예: `admin.minsdev.works`) | CNAME + `asuid.admin` TXT 추가 후 `hostname add` → `bind --validation-method CNAME` |

## 9. 배운 것 정리

1. **루트 도메인에 CNAME을 못 쓰는 건 DNS 표준 제약**이다. 그래서 A 레코드 + TXT 검증으로 우회한다.
2. **문법이 맞는 틀린 값**이 가장 위험하다. `4.230.67.12`도, 55자 hex도 시스템은 군말 없이 받는다.
   사람이 검증 못 하는 값은 **길이·문자열 비교로 기계가 검사**해야 한다.
3. **원본(권한 NS)과 사본(캐시 리졸버)을 구분**해야 "등록 실패"와 "전파 대기"를 가른다.
4. **프록시 뒤에서는 `$scheme`을 믿으면 안 된다.** TLS는 앞단에서 이미 끝났다.
5. **상대경로(`/api`)와 `window.location.origin`** 덕분에 도메인 연결에 프론트 코드 수정이 0줄이었다.
   처음 짤 때의 선택이 나중에 이자를 돌려준 사례.
6. **"에러 없음"이 "정상 진행 중"을 뜻하지는 않는다.** 루트 인증서는 `error: null` 상태로
   조용히 멈춰 있었고, 실제로는 `_dnsauth` 레코드를 기다리고 있었다.
   `-o table`에 안 보이는 필드가 원인을 쥐고 있을 수 있으니 **`-o json`으로 전체를 덤프**해야 한다.
7. **소유권 증명(`asuid`)과 인증서 발급 검증은 다른 층의 일**이다.
   전자는 Azure에게, 후자는 인증기관(CA)에게 하는 증명이다.
   `asuid`를 넣었다고 인증서가 자동으로 나오지 않는다.
8. **막히면 같은 목적의 다른 경로를 찾는다.** TXT 검증이 레코드 등록 문제로 계속 막혔을 때,
   요구사항("이 도메인을 제어함을 증명")은 그대로 두고 **수단만 HTTP 검증으로 바꿔서** 우회했다.
   수동 단계가 하나 줄어든 건 덤이다 — **사람 손이 덜 닿는 방법이 대체로 더 안정적이다.**
