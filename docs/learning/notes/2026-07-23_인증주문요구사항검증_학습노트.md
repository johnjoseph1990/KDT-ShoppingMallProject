## 1. 검증 1: 회원가입 / 로그인 / 권한 분리 (SPRINT_PLAN Day 2)

**검증 방법:** `spec-reviewer` 서브에이전트로 FUNCTIONAL_SPEC.md / SPRINT_PLAN.md와 실제 코드·테스트를 대조.

**발견한 문제:** 로그인 실패(비밀번호 틀림, 없는 이메일) 시 **401이 아니라 500**이 반환되고 있었음.

**원인 (중요 개념):**
```
BadCredentialsException 발생 (AuthController.login() 안에서)
  → GlobalExceptionHandler의 @ExceptionHandler(Exception.class) 가 먼저 잡음
  → 500 "서버 오류가 발생했습니다" 응답
  → SecurityConfig의 authenticationEntryPoint(401 처리)까지 도달 못 함
```
- `@RestControllerAdvice`(GlobalExceptionHandler)와 Spring Security 필터는 실행 순서가 다르다.
  컨트롤러 안에서 던진 예외는 Security 필터(`ExceptionTranslationFilter`)에 닿기 전에
  먼저 `DispatcherServlet`의 `@ExceptionHandler` 메커니즘을 거친다.
- 7/20에 고쳤던 401 설정 자체는 여전히 맞았지만, 그 이후 추가된 catch-all
  `@ExceptionHandler(Exception.class)`가 더 먼저 가로채면서 무력화된 것.

**수정:** `GlobalExceptionHandler.java`에 `AuthenticationException` 전용 핸들러 추가 (401).
Spring MVC는 예외 계층에서 "가장 구체적인 타입"의 핸들러를 우선하므로, 순서를 안 바꿔도
구체적인 핸들러를 추가하는 것만으로 해결됨.

**추가한 테스트** (`AuthControllerTest.java`):
- `로그인_성공_200`
- `로그인_실패_비밀번호틀림_401`
- `로그인_실패_없는이메일_401`

**추가한 테스트** (`ProductControllerTest.java`):
- `상품등록_USER권한_403` — USER 권한으로 관리자 전용 API 호출 시 403 (권한 분리 자체를 증명하는 부정 케이스가 이전엔 없었음)

**커밋:** `5711a95` — `fix: 로그인 실패 시 500으로 응답하던 회귀 버그 수정 + 인증/권한 테스트 추가`

## 2. 검증 2: 주문 상태 흐름 + 재고 처리 (SPRINT_PLAN Day 3)

**발견한 문제:** 주문 취소 경로가 두 개인데, 재고 복구는 하나에만 있었음.

| 취소 경로 | 재고 복구 |
|---|---|
| 결제 실패 → 자동 취소 (`OrderService.pay()`) | ✅ 있었음 |
| 관리자가 직접 CANCELED로 변경 (`OrderService.changeOrderStatus()`) | ❌ 없었음 (버그) |

**왜 이게 버그인가:** 관리자가 주문을 취소해도 차감됐던 재고가 영영 안 돌아옴 → "재고는 있는데 판매가 안 되는" 데이터 정합성 문제로 이어짐.

**수정:** 재고 복구 로직을 `restoreStock()` private 메서드로 추출해서 `pay()` 실패 분기와
`changeOrderStatus()`(관리자 취소) 양쪽에서 공통으로 호출하도록 변경.

- 재고 복구를 `Order` 엔티티가 아니라 `OrderService`(서비스 레이어)에 둔 이유: `Product`라는
  *다른* 엔티티를 건드리는 로직이라 `Order` 혼자만의 책임이 아니기 때문. 여러 애그리게잇에
  걸친 로직은 서비스 레이어에서 조율하는 게 정석.

**추가한 테스트** (`OrderServiceTest.java`):
- `changeOrderStatus_취소시_재고복구` — 관리자 취소 시 차감됐던 재고가 되돌아오는지
- `changeOrderStatus_SHIPPING에서_취소_예외발생` — SPRINT_PLAN이 확정한 "배송 시작 후 취소 불가" 규칙 검증

**커밋:** `bfbce3c` — `fix: 관리자 주문 수동취소 시 재고 미복구 문제 수정`

## 3. 오늘의 공통 패턴 (기억해둘 것)

**"코드가 동작한다"와 "코드가 검증됐다"는 다른 상태다.** 두 버그 모두 겉보기엔 기능이
구현돼 있어서 SPRINT_PLAN.md에 `[x]`로 체크돼 있었지만, **성공 케이스 테스트만 있고
실패/분기 케이스(negative case) 테스트가 없어서** 코드 리뷰만으로는 안 보이던 문제였다.

- 로그인: "정상 로그인 되는지"는 테스트했지만 "틀린 비밀번호로 로그인 실패하는지"는 테스트 안 함
- 주문 취소: "정상 취소되는지"는 확인했지만 "취소 후 재고가 실제로 돌아오는지"는 확인 안 함

앞으로 새 기능을 검증할 때는 **"이 기능이 실패해야 하는 상황에서 진짜로 실패하는가"**를
먼저 체크하는 습관을 들이면 좋다.
