## 1. 왜 Azure 자원을 완전 삭제했나

### 배경: 비용 vs 복구 가능성

이 프로젝트는 학습 목적이라 상시 운영 대상이 아님. Azure 비용을 0으로 만들기 위해 "일시정지"와 "완전 삭제"를 비교했다.

**검토 결과**:
- **일시정지** (앱 최소 복제본 0 + DB stop)
  - Container Apps: replicas 0으로 줄이면 과금 안 됨
  - PostgreSQL Flexible Server: stop해도 7일 후 자동 재시작 + 스토리지 비용 계속 청구
  - 결론: 정말로 비용 0이 되지 않고, 재시작 위험 존재
- **완전 삭제** (최종 결정)
  - 리소스 그룹 전체 삭제 → 자원 전부 종료 → 비용 0
  - 백업만 유지하면 재배포 시 데이터 복원 가능
  - 지금 복구 계획이 없으면 이 선택이 맞음

### 삭제 전 인벤토리

리소스 그룹 `mins-shopping-rg` 안:
- PostgreSQL Flexible Server (v16)
- Container Apps: backend, frontend (minReplicas=1)
- Container Apps 환경 + 관리형 인증서
- ACR (Azure Container Registry)
- Log Analytics 워크스페이스

별도 리소스 그룹 `kdt-shopping-mall`:
- 상품 이미지 저장소

### 단계 1: DB 백업 및 복원 검증

**왜 먼저?** 데이터를 지우기 전에 "정말 복원되는지" 검증해야 "데이터 손실"을 피할 수 있다.

**문제: 로컬에서 Azure DB에 접속 불가**

Azure DB 방화벽이 "AllowAzureServices"(0.0.0.0)만 허용하면 로컬 공인 IP로는 연결 불가. 임시 방화벽 규칙을 추가해야 한다. 규칙 이름에 목적과 날짜를 명시하면(예: `temp-backup-0924`) 언제 지워야 하는지 명확하다.

**로컬에 PostgreSQL 도구가 없으므로 Docker 이용**: postgres:16 컨테이너 안에서 pg_dump를 실행한다. 서버 버전(16) 이상이어야 호환된다.

```bash
pg_dump -h <서버> -U mins -d shoppingmall -Fc --no-owner -f /backup/shoppingmall_20260924_2157.dump
```

위 명령을 postgres:16 컨테이너 안에서 실행하려면, 호스트의 `/backup` 폴더를 컨테이너에 연결해야 덤프 파일을 호스트에 저장할 수 있다 (확인 필요).

**중요: 비밀번호 노출 방지**

`az containerapp secret show ... --secret-name pg-password`로 셸 변수에만 비밀번호를 받고, `docker run -e PGPASSWORD`처럼 값 없이 이름만 넘길 수 있다 (확인 필요: 환경변수에서 읽는지). 명령줄에 직접 노출하면 화면·로그에 남는다.

**옵션 설명**:
- `-Fc` (custom format): 압축되고 선택적 복원이 가능
- `--no-owner`: 클라우드 관리 역할이 다른 환경에서 복원 실패를 유발하므로 제외

**검증: "파일이 있다" ≠ "복원된다"**

백업 파일이 존재하는 것만으로는 부족. 실제 복원을 시도해 테이블별 행 개수가 일치하는가 확인한다.

로컬 임시 DB에서 복원 실행:
```bash
pg_restore -d shoppingmall --no-owner --no-privileges <덤프파일>
```

결과: 10개 테이블 전부 일치 (주문 11건, 회원 17명, 결제 4건, 리뷰 2건 등).

**복원 오류 처리**:

Azure DB 덤프를 로컬에 복원하면 `azure_pg_admin` 역할 GRANT 실패가 75건 발생한다. 이 역할은 Azure 전용이라 로컬 DB에 없는 것이 정상. 복원 시 `--no-privileges` 플래그를 추가해 권한 정보를 건너뛰면 오류가 0건이 된다.

### 단계 2: GitHub Actions 배포 차단

**왜 리소스 삭제 전에?** 순서가 반대면: 리소스가 없는데 push → deploy job이 "리소스 없음" 오류로 반복 실패. 들어오는 쪽(배포)을 먼저 막고 지운다.

**방법**: CI 파이프라인의 deploy job을 비활성화한다.

```yaml
deploy:
  if: false && github.event_name == 'push' && github.ref == 'refs/heads/master'
```

`&&` 앞이 false면 뒤는 평가하지 않음 (단락). deploy job이 자동 skipped된다.

**왜 job을 삭제하지 않나?**
- 배포 설정 ~100줄을 git 이력에서 복구할 필요 없음
- `false &&` 한 줄만 지우면 재배포 가능
- 코드에 "일시 중단" 의도가 명확함

**확인**: 커밋 0020815 push 후 Actions 탭 확인 → 프론트·백엔드·E2E: success, Deploy: skipped

### 단계 4: 리소스 삭제

**이미지 백업 (외부 저장소는 별도 처리)**

리소스 그룹 삭제 시 Storage 계정도 함께 지워진다. 상품 이미지를 별도 보관해야 한다.

```bash
az storage blob download-batch
```

위 명령으로 product-images 컨테이너 파일들을 다운로드한다. 개수 6개 일치 확인.

**리소스 그룹 삭제**

```bash
az group delete -n mins-shopping-rg --yes --no-wait
az group delete -n kdt-shopping-mall --yes --no-wait
```

비동기 요청만 반환되므로, 실제 삭제 완료를 따로 대기한다.

```bash
az group wait --deleted -g mins-shopping-rg
az group wait --deleted -g kdt-shopping-mall
```

"요청 보냄" ≠ "지워짐". wait 명령으로 완료를 확인해야 한다.

**서비스 주체(인증 보안주체) 정리**

배포용 서비스 주체를 찾은 뒤, 상위 앱 등록(App Registration)을 삭제한다.

```bash
az role assignment list
```

위로 배포 주체 `mins-shopping-github-actions`를 식별. 이 주체의 상위 앱 등록을 삭제하면, 서비스 주체도 함께 제거된다.

```bash
az ad app delete
```

앱 등록을 지우는 이유: 서비스 주체만 지우면 앱 등록에서 다시 만들 수 있어서다. 뿌리인 앱 등록을 삭제해 완전히 없애고, 이후 조회 시 "does not exist" 확인. Microsoft Defender 등 보안 서비스 주체는 건드리지 않는다.

## 3. 새로 배운 개념

### 개념 1: 클라우드 리소스의 비용 발생 요인 구분

**정의**: 클라우드 자원은 "켜진 시간 기반 과금"과 "저장 공간 기반 과금" 두 가지로 나뉜다.

**이번 상황에 적용**:
- Container Apps (앱): 켜진 시간만 과금 → replicas 0으로 중지 가능
- PostgreSQL + ACR (저장소): 저장 공간 과금 → 꺼도 계속 청구 → 완전 삭제 필요

**왜 필요했나**: "비용을 0으로 만들겠다"는 목표를 달성하려면 각 자원의 과금 방식을 알아야 partial solution(일부만 멈춤)과 complete solution(전부 삭제)을 구분할 수 있다. 이 프로젝트는 재운영 계획이 없으므로 완전 삭제가 맞음.

**자주 하는 실수**: 앱만 꺼두고 DB·저장소를 두면, "앱은 안 뜨지만 청구는 계속" 상태가 지속.

---

### 개념 2: Managed DB 백업의 이식성 문제

**정의**: Azure 관리형 DB의 덤프를 다른 환경(로컬, 다른 구독)에 복원할 때 권한 충돌 발생.

**문제**: 처음 로컬에서 복원했을 때 `azure_pg_admin` 역할 GRANT 오류 75건 발생. 이 역할은 Azure 전용이라 로컬 DB에 없음.

**왜 필요했나**: 권한을 제외하고만 복원해야 "타 환경에서도 복원 가능한 백업"이 된다.

**복원 명령**:
```bash
pg_restore -d <DB> --no-owner --no-privileges <덤프>
```

오류 75건 → 0건으로 해결.

**자주 하는 실수**: 전달받은 덤프 파일에 권한 정보가 이미 담겨 있으므로, 백업 단계에서 뭘 했든 복원 단계에서 `--no-privileges` 없이 진행하면 권한 오류가 나간다. Azure는 managed 역할을 쓰므로 로컬 등 타 환경에서 호환되지 않는다는 점을 간과하지 말 것.

---

### 개념 3: 임시 방화벽 규칙의 생명주기 관리

**정의**: DB 접근을 차단하는 방화벽에 임시 규칙을 추가했다가 반드시 삭제해야 한다.

**왜 필요했나**: 로컬에서 Azure DB로 백업하려면 방화벽 규칙을 열어야 한다. 작업이 끝난 뒤 규칙을 남겨두면 불필요한 IP 접근이 영구 허용되어 보안 위험.

**컨벤션**: 규칙 이름에 목적과 날짜 포함 (예: `temp-backup-0924`)

이름이 명확하면 "청소할 임시 규칙이 뭐지?" 할 때 바로 파악 가능. 의미 없는 이름의 규칙은 건드리지 못해 방치되기 쉽다.

**자주 하는 실수**: "내일 삭제하자" → 잊음 → 보안 체크에서 "미승인 IP 규칙" 지적받음.

---

### 개념 4: GitHub Secrets와 Variables의 생명주기

**정의**: CI/CD 파이프라인의 자격증명(Secret)과 설정값(Variable)은 리소스 삭제 후 수동으로 정리해야 한다.

**왜 필요했나**: 삭제된 Azure 리소스를 가리키는 자격증명(AZURE_CREDENTIALS, ACR_LOGIN_SERVER 등)은 이제 쓸 수 없다. 사용 불가 자격증명을 저장소에 두면 보안 위험 + 나중에 배포할 때 혼동.

**정리 항목**:
- Azure 인증 & 배포: AZURE_CREDENTIALS, AZURE_RESOURCE_GROUP
- ACR 레지스트리 인증: ACR_LOGIN_SERVER, ACR_USERNAME, ACR_PASSWORD
- Storage 연결: AZURE_STORAGE_CONNECTION_STRING

**자주 하는 실수**: "어차피 안 쓰니까" 하며 시크릿을 남겨두면, 나중에 다시 배포할 때 "이 시크릿이 뭐 위한 건데?" 혼란. 정리할 때 Azure 관련 항목을 전부 삭제하는 게 가장 안전.

## 4. 겪은 문제와 해결

### 문제 1: Azure CLI에서 MFA 필수 오류

**증상**:
```
조회(read) 명령은 성공 / 변경(write) 명령에서 MFA 요구
→ 오류: AADSTS50076 (Multi-Factor Authentication required)
```

**원인**: 조직 테넌트가 쓰기 작업에 MFA를 강제.

**해결**:
```bash
az login --tenant <tenant-id> --claims-challenge ...
```

브라우저 인증 팝업이 표시되고, 사용자가 직접 MFA를 완료한 뒤 셸로 돌아와 명령 재시도.

**배운 점**: "조회가 된다" ≠ "변경도 된다". 권한이 분리될 수 있으므로, 변경 작업 전에 권한을 확인해야 한다.

---

### 문제 2: Azure CLI 옵션 오타

**증상**: 명령이 인식되지 않음. 약자 옵션명(`-n` 등)이 서비스마다 다름.

**대응**: 명령이 실패했을 때 "정말 아무것도 바뀌지 않았는가"를 먼저 확인한 뒤 재시도.

구체적으로는 `--server-name` / `--name` 등 각 서비스별 옵션명을 이용.

**배운 점**: Azure CLI는 `az <service> <command> --help`로 정확한 옵션명을 매번 확인해야 한다.

## 6. 재배포·복원 시 주의사항

### 재배포 계획 (역순)

인프라 → 자격증명 → CI 활성화 순서:

1. Azure 인프라 재생성 (리소스 그룹, DB, Container Apps 환경)
2. 서비스 주체 및 GitHub Secrets 신규 생성 (고정 IP 할당받으면 DNS A 레코드도 갱신)
3. 이미지 저장소 생성 후 product-images 컨테이너에 백업 파일 업로드
4. 이미지 업로드 완료 후, `.github/workflows/ci.yml`의 `false &&` 제거
5. CI 파이프라인이 자동 배포 시작

**왜 이 순서?** 인프라가 없는데 CI를 먼저 켜면 배포가 실패한다.

### DB 복원 시 주의

## 7. (0925 추가) 뒷정리: 댕글링 DNS 레코드 삭제

### 왜 지워야 했나

Azure를 지워도 도메인 등록처(Name.com)의 DNS 레코드는 **자동으로 지워지지 않는다.**
`www` CNAME이 삭제된 Container Apps 주소를 계속 가리키면, 다른 사람이 같은 이름의
Azure 리소스를 만들어 `www.minsdev.works`를 가로챌 수 있다(서브도메인 탈취).
`asuid` TXT는 Azure의 도메인 소유 증명값이라 같이 지운다.

### 한 일

| 레코드 | 삭제 전 | 삭제 후 |
|---|---|---|
| A `@` | `4.230.67.122` (Azure 환경 IP) | `91.195.240.94` (Name.com 기본 주차 페이지, SEDO GmbH) |
| CNAME `www` | Azure 프론트 FQDN | 없음 |
| TXT `asuid` / `asuid.www` | Azure 인증값 | 없음 |
| NS 4개 (`*.name.com`) | 유지 | 유지 — 지우면 도메인 자체가 먹통 |

검증: Google DNS(`8.8.8.8`)와 원본 네임서버(`ns1psw.name.com`) 양쪽에 조회해 결과가 같음을 확인.

### 배운 점

- **"지웠다" 다음엔 "조회했다"가 와야 한다.** A 레코드를 지웠는데 조회하니 모르는 IP가
  나왔다. 소유자(RDAP)를 조회해 등록처의 기본 주차 페이지임을 확인하고 나서야 안전하다고 판단했다.
- 도메인 자동 갱신은 **의도적으로 OFF**로 바꿨다(갱신가 $50.99). 2027-08-02에 만료된다.
  재배포할 생각이면 그 전에 다시 켠다.
