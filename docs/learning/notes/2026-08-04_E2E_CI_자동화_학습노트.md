## 1. E2E를 CI에 추가하게 된 배경과 효과

### 배경: "배포 후에야 발견되던" 결함

이 프로젝트 역사상 결함 16건 중 8건이 배포된 후에야 발견됐다. 원인 분석:
- **단위 테스트(vitest)**: jsdom(가짜 브라우저 환경)에서만 검증 → 실제 렌더링, 셀렉터 동작, 화면 인가를 못 봄
- **수동 테스트**: 개발자가 손으로 클릭해 검증 → 누락·편향 가능

결과: 통합 지점(프론트→백엔드→DB)의 결함이 배포 전에 걸리지 않음.

### 해결책: Playwright E2E를 자동화

Playwright는 **실제 Chromium을 자동 조종**해 사용자처럼 동작하므로:
- 셀렉터가 실제로 엘리먼트를 찾는지 (단위 테스트로는 못 봄)
- 클릭/입력 후 화면·API·DB가 올바르게 동작하는지
- 인가(로그인 후 /admin 접근)가 안전한지

배포 전에 검증할 수 있다. CI로 자동화하면 손이 갈 필요 없다.

## 2. 새로 배운 개념

### 개념 1: GitHub Actions에서 `needs` 배포 게이팅

**정의**: 잡의 의존성을 명시하는 GitHub Actions 문법.

```yaml
deploy:
  needs: [backend, frontend, e2e]  # 이 세 잡이 모두 성공해야 deploy 시작
  ...
```

**흐름**:
1. `backend` / `frontend` / `e2e` 잡이 병렬로 실행
2. 셋 중 하나라도 실패 → `deploy` 잡이 **자동으로 스킵됨**
3. 셋 다 성공 → `deploy` 잡만 진행

**왜 필요한가**: 결함이 있는 채로 배포되는 걸 막는다. E2E가 실패하면 Azure에 배포되지 않음.

**자주 하는 실수**: `needs` 없이 모든 잡을 독립적으로 정의하면, 한 잡이 실패해도 나머지는 계속 돈다. 배포가 게이팅되지 않아 불완전한 상태가 배포될 수 있다.

---

### 개념 2: 서비스 컨테이너(Services)와 헬스 체크

**정의**: GitHub Actions가 잡 실행 중에 **옆에서 함께 띄우는 컨테이너**(주로 DB).

```yaml
services:
  postgres:
    image: postgres:16
    env:
      POSTGRES_DB: shoppingmall
      POSTGRES_PASSWORD: mins1234
    options: >-
      --health-cmd pg_isready --health-interval 10s --health-timeout 5s
```

**흐름**:
1. 러너가 PostgreSQL 16 컨테이너를 띄움
2. 헬스 체크(`pg_isready`)가 통과할 때까지 대기
3. DB가 준비되면 테스트 시작

**왜 필요한가**: DB가 아직 뜨지 않은 상태에서 테스트가 실행되면 연결 실패로 터진다. 헬스 체크로 "DB가 정말 준비됐을 때"만 진행하도록 보장.

**자주 하는 실수**: 헬스 체크를 넣지 않고 `sleep 5` 같은 고정 대기를 하면, CI 환경(느린 네트워크)에서 5초가 부족할 수 있음. 스핀락(폴링)이 더 안전.

---

### 개념 3: `process.env.CI`로 로컬과 CI 환경 구분

**정의**: GitHub Actions가 자동으로 `CI=true` 환경변수를 설정. Playwright 설정에서 이를 감지해 동작을 분기.

```javascript
const isCI = !!process.env.CI;

export default defineConfig({
  retries: isCI ? 1 : 0, // CI: 1회 재시도(네트워크 흔들림 흡수) / 로컬: 재시도 없음(실패 바로 봄)
  // ★주의: 여기서 늘린 건 "단언(expect) 대기시간"이지 테스트 전체 타임아웃이 아니다.
  //   최상위 timeout은 테스트 1건의 제한시간(기본 30초)으로 의미가 다르다.
  expect: { timeout: 10000 }, // CI 콜드 스타트로 첫 API가 느려서 기본 5초 → 10초
  reporter: isCI ? [['list'], ['html', { open: 'never' }]] : 'list', // CI: HTML 리포트 함께 / 로컬: 터미널만
  webServer: {
    reuseExistingServer: !isCI, // CI: 매번 새로 띄움 / 로컬: 이미 떠 있으면 재사용
  },
});
```

**왜 필요한가**:
- 로컬: "실패하면 원인을 빨리 보자" → 재시도 없음, 타임아웃 짧음
- CI: "간헐 실패(네트워크 타이밍)를 흡수하자" → 재시도, 타임아웃 길게

**자주 하는 실수**: 로컬 설정을 CI에 그대로 쓰면, 간헐 실패로 CI가 자주 빨간불. CI 설정을 로컬에 쓰면, 로컬 테스트가 느려 개발 흐름이 끊김.

### 개념 4: 셀렉터의 "정확도"와 "가용성" 테스트는 단위 테스트로 못 함

**관찰**: Playwright E2E를 CI에서 실행했을 때만 다음 3가지 버그가 드러남.

**버그 ①: 부분 매칭으로 인한 다중 매칭**

로컬 테스트(jsdom)에선 "이메일" 입력창이 1개로 보이지만, 실제 렌더링에선 2개:
```javascript
page.getByPlaceholder('이메일')  // 로그인 입력창 + Footer 뉴스레터("이메일 주소") 둘 다 부분매칭
```

**결과**: strict mode 위반(2개 매칭) → 테스트 실패.

**해결**: `{ exact: true }` 추가
```javascript
page.getByPlaceholder('이메일', { exact: true })  // "이메일"만 정확히 매칭
```

**버그 ②: 쿠키 준비 타이밍**

로그인 버튼 클릭 직후 곧바로 `page.goto('/admin')`하면, 세션 쿠키가 아직 안 떴을 수 있음:
```javascript
page.getByRole('button', { name: '로그인' }).click();  // 비동기, 완료 안 기다림
page.goto('/admin');  // 쿠키 아직 없음 → PrivateRoute가 /login으로 되돌림
```

**결과**: 관리자 페이지를 못 찾음.

**해결**: 로그인 완료(홈 리다이렉트)를 기다린 뒤 이동
```javascript
await page.getByRole('button', { name: '로그인' }).click();
await expect(page).toHaveURL('/');  // 홈 리다이렉트 완료 = 로그인 성공 = 쿠키 준비
await page.goto('/admin');
```

**버그 ③: Tabs.Button의 role과 중복 "담기" 버튼**

Vapor UI의 Tabs.Button은 `role="tab"`(버튼이 아님), 상품 상세의 추천 카드에도 같은 버튼 존재:
```javascript
page.getByRole('button', { name: '주문 관리' })  // Tabs.Button을 못 잡음(role이 button 아님)
```

**결과**: 요소를 못 찾음.

**해결**: 텍스트로 직접 선택하고 첫 번째만 클릭
```javascript
page.getByText('주문 관리', { exact: true }).click()  // 텍스트로 매칭(role 무관)

// "담기" 버튼 다중 매칭 → 첫 번째만 사용
page.getByRole('button', { name: '장바구니에 담기' }).first().click()
```

**왜 단위 테스트로 못 잡나?**: jsdom은 실제 렌더링 엔진이 아니라, 스타일·레이아웃·실제 role 속성이 정확하지 않다. Playwright는 Chromium 자체를 쓰므로 "실제 화면"을 본다.

## 3. CI 파이프라인 구조 요약

```
1. 트리거
   GitHub에 push → ci.yml 자동 실행

2. 병렬 단계 (backend / frontend / e2e)
   backend:
     ├─ Java 17 설치
     ├─ Gradle 빌드 & 테스트
     └─ 실패하면 다음 단계 스킵

   frontend:
     ├─ Node 20 설치
     ├─ npm ci + vitest
     └─ 실패하면 다음 단계 스킵

   e2e: (backend, frontend 성공 필요)
     ├─ PostgreSQL 16 서비스 컨테이너 띄우기 (헬스 체크 대기)
     ├─ 백엔드를 dev 프로파일로 백그라운드 기동
     ├─ /actuator/health 폴링으로 백엔드 준비 대기
     ├─ Node 20 + Playwright 설치
     ├─ npm run e2e (Playwright 설정에서 CI=true 감지해 재시도·타임아웃 적용)
     └─ 실패 → playwright-report + backend.log 아티팩트 업로드

3. 배포 단계 (needs: [backend, frontend, e2e])
   모든 테스트 성공만 진행 → Azure 배포 시작
```

## 4. CLAUDE.md 정책과의 연계

### "결함(DEF) 처리 절차" 실증

이번 작업이 CLAUDE.md의 새 "결함 처리 절차"를 구체적으로 보여줌:

```
1. 버그를 재현하는 실패 테스트 작성
2. 구현을 고쳐 테스트 통과
3. 테스트 통과 = 결함 종결 (배포 후 재검증 필요 없음)
```

위 3가지 셀렉터 버그는:
- **CI가 실패를 재현** (로컬 단위 테스트로는 안 보임)
- **원인을 파악 후 셀렉터 수정** (정확도·타이밍·role)
- **최종 5/5 통과 + 배포 그린** → 종결

과거처럼 "배포 후 재검증" 문서를 남기지 않았는데, 자동 테스트(E2E)가 그 역할을 대신하는 구조.

## 5. 부수: pre-commit 훅 개선

### 기존 문제

```bash
# 스테이징한 파일 → 포맷 → git add -u (모든 변경사항)
git add -u  # ← 함정: 스테이징 안 한 파일까지 추가됨!
```

의도: `backend/Main.java`만 커밋하려 함
결과: `backend/Other.java`, `frontend/App.tsx` 등까지 의도 안 한 파일이 커밋에 섞임 → 부분 커밋 불가능

### 개선

```bash
# 1. 스테이징된 파일만 골라서
git diff --cached --name-only --diff-filter=ACM | while read f; do
  # 2. 그 파일만 포맷하고
  spotlessApply -PspotlessFiles="$f"  # Java
  prettier --write "$f"  # JavaScript
  # 3. 그 파일만 다시 add
  git add "$f"
done
```

**결과**: 스테이징된 파일만 포맷 후 커밋 → 부분 커밋 가능.
(실제 훅은 Java를 파일마다 부르지 않고 한 번의 `spotlessApply -PspotlessFiles="여러파일"`로 묶어 처리한다 — Gradle 기동 비용이 커서.)

**자주 하는 실수 — `set -e` + 빈 목록**: 셸에 `set -e`(에러 시 즉시 종료)가 걸린 상태에서,
포맷 대상이 하나도 없을 때 재-add 루프의 `[ -n "$f" ] && git add`가 **1(거짓)을 반환**하면
스크립트가 그 자리에서 죽어 커밋이 "nothing to commit"으로 끝나버린다. 해결: `if [ -n "$FORMATTED" ]`로
목록이 빌 때는 루프 자체를 건너뛰고, 루프 본문도 `&&` 대신 `if`문으로 써서 반환값이 종료를 유발하지 않게 한다.
