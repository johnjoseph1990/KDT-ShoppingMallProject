## 1. 이번 작업에서 발견한 누락 2건

### 누락 ①: USER 권한 → 403 테스트가 없었다

기존 `AdminOrderControllerTest`에는 `미인증_401`만 있고
`USER권한_403`이 없었다. 문제: "로그인은 했지만 ADMIN이 아닌 사람이 접근하면
막히는지"를 검증하지 않은 것.

`ProductControllerTest`에는 이미 `USER권한_403` 케이스가 있었는데, 관리자 주문 컨트롤러에는
빠져 있었다 — 기능을 추가할 때 "이 패턴의 테스트가 쌍으로 있어야 한다"는 걸 놓친 사례.

**교훈**: 인가가 걸린 엔드포인트는 항상 세 가지 케이스를 세트로 작성한다:
```
1. 미인증(로그인 안 함) → 401
2. 인증됐지만 권한 부족 → 403
3. 올바른 권한으로 인증됨 → 200
```

### 누락 ②: 프론트엔드 상태 필터 UI가 없었다

백엔드 `GET /api/admin/orders?status=PAID`는 이미 구현되어 있었는데, 프론트엔드
`getAdminOrders()`가 `status` 파라미터를 받지 않아 필터를 활용하지 못하고 있었다.

`AdminPage` 주문 탭에 상태 필터 `<select>` UI를 추가하고, `getAdminOrders(page, status)`로
파라미터를 전달하도록 수정했다. 필터 변경 시 `setPage(0)`으로 첫 페이지로 리셋.

## 2. 새로 배운 개념

### 401 vs 403 — 스프링 시큐리티 기본값의 함정

스프링 시큐리티의 기본 설정은 **미로그인 접근도 403**으로 응답한다.
401(인증 실패)과 403(인가 실패)을 구분하려면 `SecurityConfig`에 명시해야 한다:

```java
.exceptionHandling(exception ->
    exception.authenticationEntryPoint(
        new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)))
```

이 설정 없이 "미인증_401" 테스트를 작성하면 테스트가 403을 받아 실패한다.
"왜 내 401 테스트가 실패하지?"의 원인이 여기 있다.

### 조건부 스프레드 패턴

```js
// status가 null이면 파라미터를 보내지 않고, 값이 있으면 포함
params: { page, ...(status && { status }) }
```

- `null && { status: null }` → `null`(falsy) → 스프레드 시 아무것도 추가 안 됨
- `"PAID" && { status: "PAID" }` → `{ status: "PAID" }` → 스프레드되어 파라미터에 포함

이 패턴은 "없으면 생략, 있으면 포함"하는 선택적 쿼리 파라미터를 만들 때 자주 쓴다.

## 3. 관리자 기능 구조 요약

```
백엔드 인가 흐름:
HTTP 요청 → SecurityFilterChain
  └─ /api/admin/**  → hasRole("ADMIN") 검사
       ├─ 미인증   → 401 (HttpStatusEntryPoint 설정 덕분)
       ├─ USER권한 → 403
       └─ ADMIN권한 → AdminOrderController.getAllOrders() 진입

프론트 인가 흐름:
/admin 라우트 → PrivateRoute(adminOnly)
  ├─ 비로그인   → /login 리다이렉트 (state.from으로 복귀 URL 전달)
  ├─ USER 역할 → / 리다이렉트
  └─ ADMIN 역할 → AdminPage 렌더링
```
