## 1. TDD 적용 방식

### 테스트 계층 구조

```
         ┌──────────────────┐
         │    E2E 스모크     │  Playwright  6파일 · 9케이스
        ┌┤   (전체 스택)     ├┐
       ┌─┤   프론트 단위     ├─┐  vitest + Testing Library  15파일 · 115케이스
      ┌──┤   Controller      ├──┐
      │  │   @WebMvcTest     │  │  백엔드 38파일 · 350케이스
      │  │   Service         │  │
      │  │   Mockito 단위    │  │
      └──┤   Repository      ├──┘
         │   @DataJpaTest    │
```

| 계층 | 도구 | 역할 |
|---|---|---|
| E2E | Playwright | 브라우저로 전체 사용자 경로 검증 |
| 프론트 단위 | vitest + RTL | 컴포넌트 동작·분기 검증 |
| Controller | @WebMvcTest | HTTP 요청/응답·보안 규칙 검증 |
| Service | Mockito | 비즈니스 로직 단위 검증 |
| Repository | @DataJpaTest | 쿼리·JPA 동작 실 DB 검증 |

**총 474개 테스트** (백엔드 350 + 프론트 115 + E2E 9)

---

### 개발 흐름

#### 기능 개발 (feat)

```
feat: 기능 구현
  ↓
test: 대응 테스트 작성 (같은 커밋 또는 직후)
  ↓
CI: 테스트 통과 확인 → 배포
```

#### 버그 수정 (DEF 처리)

```
버그 발견
  ↓
① 그 버그를 재현하는 실패 테스트 먼저 작성
  ↓
② 코드 수정 → 테스트 통과
  ↓
테스트 통과 = 결함 종결 (배포 후 재검증 불필요)
```

> **원칙:** "배포 후 발견"을 "배포 전 차단"으로 전환한다.
> 과거 DEF 16건 중 8건이 배포 후에야 발견됐던 원인은 실패 지점(통합·화면)에
> 자동 검증이 없었기 때문이다.

**실제 커밋 예시:**
```
b168c9b  test: 동시 주문 재고 차감 동시성 검증 추가
448d6c2  feat: 낙관적 락 충돌 시 자동 재시도(@Retryable) 추가

069fcf1  test: MemberControllerTest 401→400 수정
31a72c8  fix:  회원탈퇴 비밀번호 오입력 시 강제 로그아웃 버그 수정
```

## 2. 주목할 만한 테스트 5선

숫자가 아니라 **"이 테스트가 어떤 버그를 막는가"** 로 읽어야 한다.

---

### ① 동시성 — `OrderConcurrencyTest.java`

**상황:** 재고 3개짜리 상품에 10명이 동시에 1개씩 주문

**막는 버그:** `@Version` 낙관적 락 없이 동시 UPDATE → 갱신 손실(Lost Update) → 재고가 음수가 되거나 실제보다 더 많이 팔림(Oversell)

```java
// 10스레드 동시 주문 후 세 가지를 한꺼번에 검증
assertThat(재고가_마이너스가_되지_않는다(productId)).isTrue();           // 오버셀 방지
assertThat(result.success()).isLessThanOrEqualTo(initialStock);       // 성공 ≤ 초기 재고
assertThat(initialStock - 잔여_재고(productId)).isEqualTo(result.success()); // 재고 차감 = 성공 건수 1:1
```

**왜 이 테스트가 특별한가:** Mock으로는 재현 불가능하다. 실제 H2 DB + 실제 멀티스레드 + HikariCP 커넥션 풀을 띄워야 갱신 손실이 발생한다. `@SpringBootTest`에 `@Transactional`을 붙이면 안 되는 이유도 주석으로 설명되어 있다.

---

### ② 보안 설정 증명 — `SessionCookieSecurityTest.java`

**상황:** CSRF 방어를 꺼둔 채 세션 쿠키 인증 사용 → 세션 쿠키에 SameSite=Lax가 반드시 붙어야 함

**막는 버그:** SecurityConfig에 설정은 했지만 실제 톰캣 응답에 안 붙는 경우 → CSRF 공격 노출

```java
// "설정했다"와 "실제로 동작한다"는 다르다 — 실제 톰캣 HTTP 응답을 파싱
assertThat(sessionCookie.toLowerCase())
    .as("CSRF 방어가 꺼져 있으므로 세션 쿠키에 SameSite=Lax가 반드시 붙어야 한다.")
    .contains("samesite=lax");
```

**왜 이 테스트가 특별한가:** `@WebMvcTest`의 MockMvc는 톰캣을 안 띄우므로 쿠키 속성을 확인할 수 없다. `@SpringBootTest(RANDOM_PORT)`로 실제 톰캣을 띄우고 `TestRestTemplate`으로 HTTP 응답 헤더를 직접 파싱했다. `application.properties`로 설정하면 이 테스트 자체가 불가능해지는 이유도 주석에 있다.

---

### ③ 정보 유출 방지 — `GlobalExceptionHandlerTest.java`

**상황:** 예상 못 한 예외가 터졌을 때 500을 반환하되, 내부 DB 접속 문자열이나 스택 트레이스가 응답에 새면 안 됨

**막는 버그:** 500 응답에 `jdbc:postgresql://localhost:5433/shoppingmall` 같은 내부 정보가 노출 → 공격자에게 인프라 정보 제공

```java
mockMvc
    .perform(get("/probe/boom"))
    .andExpect(status().isInternalServerError())
    .andExpect(jsonPath("$.message").value("서버 오류가 발생했습니다. 잠시 후 다시 시도해주세요."))
    // 핵심: 응답 "전체"에 내부 예외 메시지가 섞이지 않았는지
    .andExpect(content().string(not(containsString("jdbc:postgresql"))));
```

**왜 이 테스트가 특별한가:** "500이 나온다"를 검증하는 게 아니라 "내부 정보가 절대 새지 않는다"를 `not(containsString)`으로 검증했다. 두 개의 다른 AccessDeniedException 분기(스프링 영문 메시지 → 한국어 교체 vs 서비스가 직접 쓴 한국어 메시지 → 그대로 전달)도 각각 별도 테스트로 커버한다.

---

### ④ 프론트엔드 인가 — `PrivateRoute.test.jsx`

**상황:** 일반 사용자가 `/admin`에 접근하면 홈으로, 비로그인 사용자가 보호된 경로에 접근하면 `/login`으로 리다이렉트해야 함

**막는 버그:** `<PrivateRoute>`를 App.jsx 라우팅에서 빠뜨려도 단위 테스트가 없으면 아무도 모름 → 일반 사용자가 관리자 화면을 그대로 봄

```jsx
// "로그인 화면이 보인다" 만으로는 부족하다 — 보호된 내용이 "새지 않았다"를 못박아야 한다
expect(screen.getByText('로그인 화면')).toBeInTheDocument()
expect(screen.queryByText('주문 내역 상세')).not.toBeInTheDocument() // ← 이게 핵심
```

**왜 이 테스트가 특별한가:** 리다이렉트 확인만으로 끝내지 않고 보호된 콘텐츠가 DOM에 한 글자도 렌더링되지 않았음을 함께 검증한다. 가장 위험한 시나리오(로그인은 됐지만 ADMIN 권한 없는 사용자가 /admin 접근)를 명시적으로 테스트한다.

---

### ⑤ 경계값 TDD — `pagination.test.js`

**상황:** `isLastPage()` 함수 — off-by-one 실수가 가장 나기 쉬운 곳

**막는 버그:** DEF-9에서 `orders.length === 0` 조건을 쓰다가 "마지막 페이지인데 목록이 비어있지 않은" 경우 "다음" 버튼이 열려있던 버그를 재현·방지

```js
// 이 파일이 구현보다 먼저 있는 이유(TDD): 어떤 입력에 어떤 답이 나와야 하는지를
// 코드로 먼저 못 박아두고 그걸 만족시키는 식을 쓰는 편이 안전하다.
expect(isLastPage(4, 5)).toBe(true)   // 마지막 페이지
expect(isLastPage(3, 5)).toBe(false)  // 마지막 직전
expect(isLastPage(0, 1)).toBe(true)   // DEF-9 재현 조건
expect(isLastPage(3, 1)).toBe(true)   // 필터로 페이지 수 줄어듦
expect(isLastPage(0, undefined)).toBe(true)  // 방어: 모를 땐 잠근다
```

**왜 이 테스트가 특별한가:** 구현 전 테스트 작성(TDD)이 커밋 주석에 명시되어 있고, 실제 버그(DEF-9)를 재현하는 케이스가 주석으로 표시되어 있다. 방어적 처리("모를 땐 잠근다")의 이유까지 설명한다.

| `learning-writer` | 학습노트 산문 작성 |

---

### 일반적인 AI 활용 vs 이 프로젝트

**일반적인 방식:**
```
개발자 → "이 코드 짜줘" → AI → 복붙 → 끝
```

**이 프로젝트 방식:**
```
기능 구현
  → security-reviewer 게이트 (인증·결제 변경 시)
  → test-writer로 TDD 테스트 작성
  → CI 자동 검증 (474개 테스트)
  → E2E 통과 확인
  → Azure 자동 배포
  → 결함 발생 시 회귀 테스트 먼저 작성
  → fix → 테스트 통과 = 종결
```

**차이:** AI를 "도구로 사용"한 것이 아니라 **개발 프로세스 자체를 AI 중심으로 설계**했다.

## 4. 심사관 어필 포인트 분석

객관적으로 "이게 어필이 되는가"를 평가한다.

| 항목 | 평가 | 이유 |
|---|---|---|
| 474개 테스트 숫자 | ⭐⭐⭐ 보통 | KDT 기준으론 많지만 숫자 자체는 차별화 포인트가 아님 |
| **동시성 테스트** | ⭐⭐⭐⭐⭐ 강력 | 멀티스레드 재고 손실 — 실서비스 버그, 부트캠프에서 거의 안 함 |
| **보안 설정을 테스트로 증명** | ⭐⭐⭐⭐⭐ 강력 | "설정했다"와 "동작한다"의 차이를 이해한다는 걸 보여줌 |
| **정보 유출 not(containsString)** | ⭐⭐⭐⭐ 좋음 | 500 에러 방어를 "상태코드"가 아닌 "내용"으로 검증 |
| E2E가 배포 게이트 | ⭐⭐⭐⭐ 좋음 | CI에서 배포 전 차단 — 실무 수준 |
| 7종 전문 에이전트 | ⭐⭐⭐⭐ 좋음 | 단순 AI 코딩 보조가 아닌 프로세스 설계 |
| **DEF 처리 절차** | ⭐⭐⭐⭐ 좋음 | "버그 → 재현 테스트 → 수정 → 통과 = 종결" 사이클 문서화 |
| 한계 솔직히 기술 | ⭐⭐⭐⭐ 좋음 | "한계도 안다"는 성숙도를 보여줌 |

### 심사관이 볼 때 차별화되는 포인트 두 가지

**1. "설정"이 아닌 "증명"**

보통은 "SameSite 쿠키 설정했습니다"로 끝낸다.
이 프로젝트는 **실제 톰캣 HTTP 응답을 파싱해서 `samesite=lax`가 붙어 있음을 자동으로 증명**한다.
설정과 동작의 차이를 이해했다는 신호다.

**2. 동시성 버그를 테스트로 재현**

JPA의 `@Version`, `@Retryable`을 쓰는 프로젝트는 있다.
하지만 **"10스레드 동시 주문에서 재고 음수가 절대 안 된다"를 실제 멀티스레드 테스트로 검증**한 프로젝트는 드물다.
Mock으로 흉내내지 않고, 실제 H2 + 커넥션 풀 + 락 경쟁을 재현했다.

---

### 솔직한 한계

- 에이전트가 **주도적으로 행동하지 않는다** — 사람이 "언제 어떤 에이전트를" 판단
- Devin·SWE-agent 같은 완전 자율 에이전트와는 다르다
- 실수는 여전히 발생한다
  - `401→400` 수정 후 테스트 업데이트를 빠뜨려 CI가 깨졌다 (test 커밋으로 수정)

## 5. 한 줄 요약

> **"기능 구현과 테스트를 항상 쌍으로 커밋하고, 동시성·보안·정보유출까지 테스트로 증명하며, 7개 전문 에이전트가 코드 품질을 계층별로 검토하고, CI가 474개 테스트를 배포 게이트로 막아 '배포 후 발견'을 '배포 전 차단'으로 전환했다."**
