핵심 답변 먼저

❌ 코드를 수정하면 바로 올라가지 않습니다.
파일을 저장하거나 IDE에서 수정하는 것만으로는 아무 일도 생기지 않습니다.

✅ git push origin master 를 해야 자동 배포가 시작됩니다.
Push 순간 GitHub이 감지하고, 테스트 → 배포 파이프라인이 자동 실행됩니다.

단, 테스트·커버리지 조건을 모두 통과해야만 배포까지 진행됩니다.
실패하면 배포 없이 멈춥니다.

전체 흐름 한눈에

💻 내 PC에서 코드 수정 후 git push origin master
↓
GitHub이 push 감지 → Actions 자동 시작
🤖 GitHub Actions 실행 (ci.yml)
↓
CI 백엔드 테스트 + 커버리지 & 프론트엔드 테스트 + 빌드
↓
둘 다 통과해야만 ↓
CD Docker 빌드 → ACR 푸시 → Azure 배포
↓
🌐 클라우드에서 새 버전 운영 중

CI / CD 가 뭔가요?

CI · Continuous Integration

지속적 통합

코드를 합칠 때마다 자동으로 테스트를 돌려서, 이 코드가 괜찮은지 빠르게 검증한다.

  • 포맷 규칙 위반 검사 (Spotless / Prettier)
  • 단위·통합 테스트 자동 실행
  • 커버리지 60% 미달 시 실패
  • PR / push 때마다 실행
CD · Continuous Deployment

지속적 배포

CI를 통과하면 사람이 개입하지 않고 자동으로 서버에 반영한다.

  • master push 때만 실행 (PR은 해당 없음)
  • Docker 이미지 빌드 & 저장
  • Azure Container Apps에 새 버전 배포
  • 롤백용 이미지 이력 유지

비유: CI = 원고 교정자, CD = 출판 인쇄기.
교정을 통과한 원고만 인쇄기로 넘어가고, 인쇄는 자동으로 됩니다.

GitHub Actions

# .github/workflows/ci.yml

on:
  push:
    branches: [ master ]   # push 감지
  pull_request:
    branches: [ master ]   # PR 감지

jobs:
  backend:                   # CI 잡 1
    runs-on: ubuntu-latest
    steps:
      - run: ./gradlew check    # 포맷+테스트
      - run: ./gradlew jacocoTestCoverageVerification

  deploy:                    # CD 잡
    needs: [backend, frontend] # CI 통과 후만
    if: github.event_name == 'push'
📄

ci.yml 파일 하나로 모든 자동화를 정의

GitHub 서버에서 실행되므로, 내 PC가 꺼져 있어도 파이프라인은 돌아갑니다.

🔗

needs: [backend, frontend]

CI 잡 두 개가 모두 통과해야만 deploy 잡이 실행됩니다. 하나라도 실패하면 배포 없이 멈춥니다.

🎯

PR vs Push 차이

PR → CI만 실행 (안전 검증)
master에 push → CI + CD 실행 (검증 + 배포)

Docker 이미지

📦

이미지란?

앱 코드 + 실행 환경(JDK, Node, OS 설정)을 하나의 파일로 묶은 것.

어디서 실행해도 동일한 환경이 보장됩니다.

🏷️

git SHA 태그

이미지 이름에 commit 해시를 붙입니다.

backend:a3f2c1d...

어떤 커밋이 운영 중인지 추적하고, 문제 발생 시 이전 이미지로 롤백할 수 있습니다.

🚢

빌드 흐름

① Dockerfile 읽기
② 소스 코드 복사
③ 빌드(컴파일/번들)
④ 이미지 완성 → ACR로 전송 

# 백엔드 이미지 빌드 + ACR 푸시 (ci.yml 158번 줄)
docker build -t $ACR_LOGIN_SERVER/backend:${{ github.sha }} ./backend
docker push  $ACR_LOGIN_SERVER/backend:${{ github.sha }}
# ↑ ${{ github.sha }} = 현재 커밋의 해시 (예: a3f2c1d9b8e7...)

ACR — Azure Container Registry

🗄️

Docker 이미지 창고

GitHub에 소스 코드를 올리듯,
빌드된 Docker 이미지를 ACR에 올립니다.

Docker Hub의 Azure 전용 버전이라고 이해하면 됩니다.

🔄

배포 흐름에서의 역할

CI/CD가 이미지를 ACR에 push
→ Azure Container Apps가 ACR에서 이미지를 pull
→ 앱이 새 버전으로 교체됩니다.

GitHub Actions
(이미지 빌드)
↓ docker push
🗄️ ACR
(이미지 저장소)
↓ docker pull
Azure Container Apps
(앱 실행)

Azure Container Apps

🌐

실제 앱이 돌아가는 클라우드 서버

백엔드(Spring Boot)와 프론트엔드(React+nginx) 각각 하나씩 Container App으로 운영됩니다.

배포 명령으로 "이 이미지 써" 라고 지시하면 자동으로 재시작됩니다.

🔗

내부 통신 (Internal FQDN)

프론트(nginx) → 백엔드 API를 호출할 때
인터넷을 거치지 않고 Azure 내부 네트워크로 직접 연결합니다.

배포 시 백엔드 내부 주소를 프론트에 환경변수로 자동 주입합니다. 

# 백엔드 배포 (ci.yml 174번 줄)
az containerapp update \
  --name backend \
  --resource-group $AZURE_RESOURCE_GROUP \
  --image $ACR_LOGIN_SERVER/backend:${{ github.sha }}
# ↑ "backend 앱의 이미지를 방금 푸시한 버전으로 교체해" 라는 명령

GitHub Secrets

🔒

API 키·비밀번호를 코드에 직접 쓰면 안 됩니다

코드는 GitHub에 공개될 수 있기 때문에,
민감한 값은 GitHub 설정에 따로 저장하고
실행 시점에 환경변수로 주입하는 방식을 씁니다.

실제 사고 사례 (2026-08-02)
VITE_TOSS_CLIENT_KEY 시크릿이 등록되지 않은 채 배포되어,
운영 환경에서 결제가 전부 불가능했습니다.
→ 시크릿 누락을 배포 전에 검사하는 코드를 ci.yml에 추가했습니다.

시크릿 이름 용도
AZURE_CREDENTIALS Azure CLI 인증 (Service Principal)
ACR_LOGIN_SERVER 컨테이너 레지스트리 주소
ACR_USERNAME ACR 로그인 아이디
ACR_PASSWORD ACR 로그인 비밀번호
TOSS_SECRET_KEY 토스페이먼츠 결제 서버키
VITE_TOSS_CLIENT_KEY 토스페이먼츠 클라이언트키 (프론트 번들에 포함)

배포되려면 무엇을 통과해야 하나?

백엔드

  • 1 Spotless 포맷 검사
    Google Java Format 규칙 위반 시 실패
  • 2 JUnit 테스트 전체 통과
    실패한 테스트가 하나라도 있으면 중단
  • 3 JaCoCo 커버리지 60% 이상
    미달 시 빌드 실패 (하드 게이트)

프론트엔드

  • 1 Prettier 포맷 검사
    npm run format:check 위반 시 실패
  • 2 Vitest 테스트 전체 통과
    npm run test:run 실패 시 중단
  • 3 Vite 빌드 성공
    번들링 오류 시 실패

커버리지가 60% 미만이면 테스트를 아무리 잘 써도 배포가 막힙니다.
반대로 말하면, 테스트를 충분히 쓰면 배포가 자동으로 이루어집니다.
